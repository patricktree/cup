# Account holder's name for avatar initials

> Historical research, incorporated 2026-10-28. Cup adopted the recommendation through [spec #89](https://github.com/patricktree/cup/issues/89), built in [#101](https://github.com/patricktree/cup/pull/101) (`8cccf1e`): the avatar reads `user_metadata.name`, else `full_name`, from the Supabase session, Cup stores no name, and a pure function takes the first letter grapheme of the first and last whitespace-separated words, with a `UserRound` glyph when no name is usable; the local test account and the E2E fake auth provider now carry a name. See [account chrome](../architecture/web-app.md#account-chrome). That Android native sign-in stores `name` is still unobserved on a device. Repository observations below describe `dcec7ecd`.

[Original investigation](https://github.com/patricktree/cup/blob/92f10bb3bca46fc0e24b0b2c258ac870f6bd2449/docs/research/avatar-initials-name-source.md).

Research date: 2026-10-27, for [issue #81](https://github.com/patricktree/cup/issues/81) of the [Recents redesign map](https://github.com/patricktree/cup/issues/79). Repository observations are from `main` at `dcec7ecd`. Supabase Auth source is `supabase/auth` `master` at `c3348e8f`; the hosted Supabase project may run an older release, which was not checked. `@capawesome/capacitor-google-sign-in` source is the published 0.1.4 (`capawesome-team/capacitor-plugins` at `7c1937ed`). Google and Supabase documentation was read on the research date. No real Google sign-in was performed and no stored user was inspected.

## Question

Where can the web app get the account holder's name to show avatar initials (the first letter of the first name and of the last name, such as "vh" for Verena Handler-Kunze, with a glyph when no name is known)? Does Supabase's Google sign-in put `full_name`, `name`, `given_name` or `family_name` in the session, does Cup's account record or snapshot hold a name, how should initials be derived for one-word, hyphenated, multi-part and non-Latin names, and what would storing a name in Cup mean for privacy and account deletion?

## Answer

- The signed-in Supabase session already carries the name: `session.user.user_metadata.name`, duplicated as the deprecated `full_name`. Both Cup sign-in paths (web and iOS OAuth, Android native ID token) fill it from Google's `name` claim.
- It does **not** carry `given_name` or `family_name`. Google sends both in its ID token, but Supabase Auth's Google provider drops them; an open upstream pull request would add them. Initials therefore have to be split out of the full display name.
- Cup holds no name anywhere: the account snapshot has `accountId`, `subject`, `createdAtMs`, lifecycle state and balance only, and the account page already reads `session.user.email` straight from the session.
- The local test account and the E2E fake auth provider have empty `user_metadata`, so they show the fallback glyph unless the build gives them a name.
- Recommendation: read the name from the session on the client and store nothing in Cup. Derive initials from the first and last whitespace-separated words, one grapheme each, skipping words without a letter; a one-word name gives one initial and a missing or letterless name gives the glyph.

## What Cup has today

- **Account record and snapshot.** [`accountIdentitySchema`](../../libs/accounts/src/domain/account-contracts.ts) is `accountId`, `subject` and `createdAtMs`; [`accountSnapshotSchema`](../../libs/accounts/src/domain/account-contracts.ts) adds `state`, `executionEpoch`, `recoveryDeadlineMs` and `balance`, and is `.strict()`. The listener API's [`accountSnapshotSchema`](../../libs/listener-api.routes/src/contracts.ts) only narrows the balance. No Cup storage holds a name or email for an active account; the email the account lifecycle stores is the deletion-notice address captured at confirmation ([`account-lifecycle.ts`](../../libs/accounts/src/storage/account-lifecycle.ts)), and the coordinator blanks it once the notice is handled ([`deletion-coordinator.ts`](../../libs/registry/src/account-deletion/deletion-coordinator.ts)).
- **Session on the client.** The [session facade](../../apps/web-app/src/auth/account-session.ts) exposes the supabase-js `Session`, whose `user` includes `user_metadata` and `app_metadata`; `useAccountSession()` in [`hooks.ts`](../../apps/web-app/src/auth/hooks.ts) gives it to components. The [account page](../../apps/web-app/src/routes/_shell.account.tsx) already renders `session.user.email` from it, so reading `user_metadata.name` the same way follows an existing pattern. The session is persisted in `localStorage` on the web and in secure storage on Android, and sign-out clears it ([authentication](../architecture/authentication.md#client-session-lifecycle)).
- **Sign-in paths.** The [web adapter](../../apps/web-app/src/platform/account-auth.web.ts) calls `signInWithOAuth({ provider: "google" })`, and the [iOS adapter](../../apps/web-app/src/platform/account-auth.ios.ts) re-exports it. The [Android adapter](../../apps/web-app/src/platform/account-auth.android.ts) gets a Google ID token from `@capawesome/capacitor-google-sign-in` and exchanges it with `signInWithIdToken`. The plugin's result also carries `displayName`, `givenName` and `familyName` from Android Credential Manager's `GoogleIdTokenCredential` ([`SignInResult.java`](https://github.com/capawesome-team/capacitor-plugins/blob/7c1937ed10b7de86ca2c1cdc3539a2735fd69a00/packages/google-sign-in/android/src/main/java/io/capawesome/capacitorjs/plugins/googlesignin/classes/results/SignInResult.java)), but Cup discards the result apart from the ID token, and those fields exist only at sign-in on Android.
- **Worker.** [`account-auth.ts`](../../libs/api-server/src/http/account-auth.ts) reads `app_metadata.provider` and `email` from the JWT and nothing from `user_metadata`.
- **Test identities.** [`dev-services.ts`](../../tooling/env-setup/src/dev-services.ts) creates the local test account with only `email`, `password` and `email_confirm`; the E2E [fake auth provider](../../qa/e2e/test-e2e/auth-provider.ts) and [`account-session.test.ts`](../../apps/web-app/src/auth/account-session.test.ts) use `user_metadata: {}`.

## What Google provides

Google's [OpenID Connect reference](https://developers.google.com/identity/openid-connect/openid-connect) (last updated 2026-06-15) defines `name` as "The user's full name, in a displayable form", provided when the scope includes `profile` or the token comes from a refresh, and notes that it "is never guaranteed to be present". `given_name` ("given name(s) or first name(s)") and `family_name` ("surname(s) or last name(s)") "Might be provided when a name claim is present". The [Sign in with Google JavaScript reference](https://developers.google.com/identity/gsi/web/reference/js-reference) (last updated 2026-09-01) shows a credential payload with `name`, `given_name` and `family_name`. Android's [`GoogleIdTokenCredential`](https://developers.google.com/identity/android-credential-manager/android/reference/com/google/android/libraries/identity/googleid/GoogleIdTokenCredential) exposes `getDisplayName()`, `getGivenName()` and `getFamilyName()` without non-null annotations; the [Sign in with Google for Android guide](https://developer.android.com/identity/sign-in/credential-manager-siwg) says only that users consent to share "their profile information" and does not list the ID token's claims.

## What Supabase Auth stores

- **Scopes.** The Google provider always requests `email` and `profile` ([`google.go`](https://github.com/supabase/auth/blob/c3348e8f1cb31454e9783e4eb9eab1e71ad9652f/internal/api/provider/google.go)), so the OAuth path gets a `name` claim whenever Google provides one.
- **Claims kept.** For both the OAuth code exchange and the ID token grant (`IdTokenGrant` in [`token_oidc.go`](https://github.com/supabase/auth/blob/c3348e8f1cb31454e9783e4eb9eab1e71ad9652f/internal/api/token_oidc.go) calls `ParseIDToken`), Google tokens go through `parseGoogleIDToken` in [`oidc.go`](https://github.com/supabase/auth/blob/c3348e8f1cb31454e9783e4eb9eab1e71ad9652f/internal/api/provider/oidc.go). Its `googleUser` struct decodes only `sub`, `iss`, `name`, `picture`, `email`, the two verified flags and `hd`, and maps them to `name`, `full_name` (marked "To be deprecated"), `picture`, `avatar_url`, `provider_id`, `iss` and `sub`. The shared `Claims` struct in [`provider.go`](https://github.com/supabase/auth/blob/c3348e8f1cb31454e9783e4eb9eab1e71ad9652f/internal/api/provider/provider.go) has `given_name` and `family_name` fields, but the Google provider never fills them.
- **Upstream fix pending.** [supabase/auth#2501](https://github.com/supabase/auth/pull/2501), "populate given_name, family_name, and locale in user metadata", opened 2026-04-23, was still open on the research date.
- **Where it lands.** `createAccountFromExternalIdentity` in [`external.go`](https://github.com/supabase/auth/blob/c3348e8f1cb31454e9783e4eb9eab1e71ad9652f/internal/api/external.go) writes the mapped claims to the identity's `identity_data` and merges them into the user's `user_metadata` on sign-up, on linking, and on every later sign-in of an existing user. A name changed at Google therefore reaches Cup at the next sign-in. Because the claims are mapped with `omitempty`, an empty value never removes a stored key ([`UpdateUserMetaData` in `user.go`](https://github.com/supabase/auth/blob/c3348e8f1cb31454e9783e4eb9eab1e71ad9652f/internal/models/user.go)).
- **Where the client sees it.** Supabase stores user metadata in `auth.users.raw_user_meta_data` and returns it as `user_metadata` ([Managing user data](https://supabase.com/docs/guides/auth/managing-user-data)); access tokens may carry it as the optional `user_metadata` claim ([JWT fields](https://supabase.com/docs/guides/auth/jwt-fields)).
- **User-writable.** `updateUser` with `data` merges into `user_metadata` (`params.Data` in [`internal/api/user.go`](https://github.com/supabase/auth/blob/c3348e8f1cb31454e9783e4eb9eab1e71ad9652f/internal/api/user.go)). That rules it out for authorization but is harmless for a person's own avatar.

Unknown: whether the ID token Android Credential Manager returns to Cup includes `name`. Google's general reference suggests it does when profile information is shared, and Supabase would store it the same way, but this was not observed. Signing in once on Android and checking the user's `user_metadata` in the Supabase dashboard settles it.

## Deriving initials

With only a display name available, the client has to guess which words are the first and last names. A rule that takes the first and last whitespace-separated words matches the design's example and most Western names, and fails gracefully elsewhere:

1. Take `user_metadata.name`, else `user_metadata.full_name`, if it is a string; normalize it to NFC and trim it.
2. Split it on whitespace (`/\s+/u`). Do not split on hyphens, so a hyphenated given or family name contributes its first letter only.
3. For each word, take its first grapheme cluster that starts with a letter (`/^\p{L}/u`), using `Intl.Segmenter` with `granularity: "grapheme"`; drop words without one, such as an emoji. A word like `(Bob)` contributes `B`.
4. Use the first remaining word's grapheme, plus the last remaining word's grapheme when there are at least two words. No word left means the glyph.
5. Lowercase for display, as the design does, preferably with CSS `text-transform: lowercase`, which applies language-specific case mapping such as Turkish dotted and dotless i when the element's `lang` is known ([MDN `text-transform`](https://developer.mozilla.org/en-US/docs/Web/CSS/text-transform)). Scripts without case are unaffected.

Grapheme segmentation keeps a decomposed `É` (E plus U+0301), a surrogate-pair Han character, a Hangul syllable written as jamo, or an Indic letter with its vowel sign together, where `string[0]` or `charAt(0)` would split them. `Intl.Segmenter` is Baseline widely available since April 2024 ([MDN](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/Intl/Segmenter)).

| Display name                     | Result | Note                                                                         |
| -------------------------------- | ------ | ---------------------------------------------------------------------------- |
| Verena Handler-Kunze             | vh     | The design's example                                                         |
| Cher                             | c      | One word gives one initial                                                   |
| Jean-Luc Picard                  | jp     | Hyphenated given name                                                        |
| Ludwig van Beethoven             | lb     | Particles are skipped by taking the last word                                |
| María José García López          | ml     | Spanish naming would expect the first surname (g); the rule cannot know      |
| Martin Luther King Jr.           | mj     | Suffixes are taken as the last name; a suffix list is possible but brittle   |
| 王小明                           | 王     | No spaces: one grapheme, the family name                                     |
| 山田 太郎                        | 山太   | Family-name-first order is kept as written                                   |
| 김민준                           | 김     | Hangul without spaces: one syllable                                          |
| محمد عبد الله                    | ما     | Arabic letters show in isolated form; `dir="auto"` keeps right-to-left order |
| Anna 🌸                          | a      | Letterless words are dropped                                                 |
| (missing, empty or only symbols) | glyph  | Also the local test account today                                            |

For names in scripts without case and without spaces between given and family names, one grapheme is what the rule yields anyway. Whether to show one grapheme for all such scripts, rather than two for space-separated ones like the Japanese example, is a product choice for the spec. The initials are decoration: the avatar link's accessible name should say what it opens (for example "Account"), not read out the letters.

## Storing a name in Cup versus reading it from the session

| Concern                       | Read from the session                                                                                                                                                                                       | Store in Cup's account                                                                                                                                                                                                         |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| New personal data held by Cup | None; Supabase already holds the name in `auth.users` and `auth.identities`, and the client in its stored session                                                                                           | A new personal-data field in the account Durable Object                                                                                                                                                                        |
| Freshness                     | Follows Google at the next sign-in, through Supabase                                                                                                                                                        | Needs a write path, from the client or by reading the JWT on each request, and goes stale without one                                                                                                                          |
| Account deletion              | Covered: the registry hard-deletes the Supabase user (`should_soft_delete: false` in [`supabase-identity.ts`](../../libs/registry/src/providers/supabase-identity.ts)), and sign-out clears the client copy | Account erasure removes account records, so it would be covered, but every new field must be checked against the erasure, notice-redaction and 90-day receipt rules in [account deletion](../architecture/account-deletion.md) |
| While deletion is scheduled   | The signed-out client shows no avatar                                                                                                                                                                       | The stored name lingers for the seven-day recovery window                                                                                                                                                                      |
| Other devices and platforms   | Each device's session carries it after a sign-in or token refresh                                                                                                                                           | Same data, one more copy                                                                                                                                                                                                       |
| Contract change               | None; the account snapshot stays `.strict()` and nameless                                                                                                                                                   | Snapshot, API contract and tests change                                                                                                                                                                                        |

Storing a name would add data that Cup does not need for any other purpose, which works against data minimization, while giving the avatar nothing the session lacks. It would only pay off if Cup later needs the name server-side, such as in email greetings, or wants to let people choose their own display name; neither is planned. The repository has no privacy policy text that names which profile data Cup processes, so nothing there needs updating for the session approach.

Reading `given_name` and `family_name` some other way is not worth it: the web client never sees Google's ID token, the Google access token (`provider_token`) is only present right after the OAuth return and would need a People API or userinfo call per sign-in, and the Android plugin's fields exist only on Android and only at sign-in. If supabase/auth#2501 ships, the derivation can prefer `given_name` and `family_name` with the full-name split as the fallback, without other changes.

## Recommendation for the spec

- Read the name from `useAccountSession()` as `user_metadata.name ?? user_metadata.full_name`; store nothing in Cup and leave the account snapshot unchanged.
- Derive initials with the rule above in one pure function with unit tests covering the table's cases, and render the glyph when it returns nothing.
- Decide whether scripts without spaces or case get one grapheme, and whether the local test account and the E2E fake auth provider get a `user_metadata.name` (the Supabase admin create-user call accepts `user_metadata`) so local development and E2E tests show initials rather than only the glyph.
- Verify once on Android that a natively signed-in user has `user_metadata.name`.
