Research date: 2026-11-14, for [issue #367](https://github.com/patricktree/cup/issues/367), following the hands-on findings in [issue #350](https://github.com/patricktree/cup/issues/350). Repository state: `main` at `8e5c815d`. Sources are read at pinned commits: `@sentry/capacitor` [`4.6.0`](https://github.com/getsentry/sentry-capacitor/tree/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7) (which bundles `io.sentry:sentry-android:8.64.0` and `sentry-apple-binaries` `9.28.0`), sentry-java [`8.64.0`](https://github.com/getsentry/sentry-java/tree/683908daaa63add97ca9a1710ab4a6898ada1c2b), sentry-cocoa [`9.28.0`](https://github.com/getsentry/sentry-cocoa/tree/61e8cb02434b26fb34c58126d883e5663cfde238), sentry-javascript [`10.76.2`](https://github.com/getsentry/sentry-javascript/tree/042e228984d2d11fecc1de849c59bfbe8a1c42af) and [`11.12.0`](https://github.com/getsentry/sentry-javascript/tree/8bebd2951dc1ae1fb9406c51cb3f0b2332f9575e), Relay `master` at [`d46ae1fd`](https://github.com/getsentry/relay/tree/d46ae1fd35be2f701d9c4876b9de384dfee04e50) (2026-11-13, after release `26.10.1`), and Sentry `master` at [`73b55402`](https://github.com/getsentry/sentry/tree/73b55402452d544d70f534b457f66b84336743e9). Nothing was run against Sentry for this note: every behaviour below is read from source or documentation, and the items in [Needs hands-on confirmation](#needs-hands-on-confirmation) still need a device.

## Question

How do events from Cup's Android and iOS Capacitor shells reach Sentry without Sentry storing city-level geolocation, and without the native SDK's installation ID as `user.id`? The candidates were a JS fetch transport through the telemetry tunnel, native-side options, server-side scrubbing or settings, and an explicit user that suppresses the installation ID.

## Answer

**Relay derives geolocation from the connection IP whenever the event carries no IP of its own, and no setting turns that off.** `normalize_user_geoinfo` looks up `user.ip_address`, or else the connection's client IP, and the caller passes the client IP unfiltered by "Prevent storing IP addresses" ([`event.rs` L282–L298](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-event-normalization/src/event.rs#L282-L298), [L508–L528](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-event-normalization/src/event.rs#L508-L528)). That setting only switches off IP _inference_ into `user.ip_address` ([`processing/utils/event.rs` L258–L263](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-server/src/processing/utils/event.rs#L258-L263)). This explains #350 exactly: `ip_address: null` changes nothing for events from the device, and tunnel events get the country of Cloudflare's egress IP. Sentry's docs say the same and name the fix: "Geographic information is extracted from the user's IP address. This occurs even if the setting to stop storing IP addresses is turned on", and recommend an Advanced Data Scrubbing rule ([server-side scrubbing](https://docs.sentry.io/security-legal-pii/scrubbing/server-side-scrubbing/#geographic-information)).

**An Advanced Data Scrubbing rule removes city, subdivision and region from every event, whichever path it took.** Relay scrubs after it normalizes, so the rule sees the geo that normalization just added: errors run `normalize` then `scrub` ([`errors/mod.rs` L133–L141](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-server/src/processing/errors/mod.rs#L133-L141)), transactions likewise ([`transactions/mod.rs` L134–L168](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-server/src/processing/transactions/mod.rs#L134-L168)). Every `Geo` field is `pii = "true"` ([`user.rs` L9–L28](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-event-schema/src/protocol/user.rs#L9-L28)), so explicit selectors reach them. Cup's masking decision keeps country and drops anything finer ([#341](https://github.com/patricktree/cup/issues/341), decision 5), so the rule should remove `$user.geo.city`, `$user.geo.subdivision` and `$user.geo.region` and keep `country_code`. Terraform cannot set it: the rule set is the organization's `relayPiiConfig` string, written through `PUT /api/0/organizations/{org}/` ([`organization_details.py` L169, L321](https://github.com/getsentry/sentry/blob/73b55402452d544d70f534b457f66b84336743e9/src/sentry/core/endpoints/organization_details.py#L169)), the same API call that sets `scrubIPAddresses`.

The user set from JS reaches native through scope sync, but only `id`, `email`, `username` and `ip_address` cross the bridge, plus other keys as string `data` ([`wrapper.ts` L215–L235](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/src/wrapper.ts#L215-L235), [Android `setUser`](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/android/src/main/java/io/sentry/capacitor/SentryCapacitor.java#L185-L231), [iOS `setUser`](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/ios/Sources/SentryCapacitorPlugin/SentryCapacitorPlugin.swift#L391-L414)). `Sentry.setUser({})` does create an empty native user on both platforms, which is enough on iOS but not on Android. In JS, an empty user is dropped from the event ([`scopeData.ts` L142–L143](https://github.com/getsentry/sentry-javascript/blob/042e228984d2d11fecc1de849c59bfbe8a1c42af/packages/core/src/utils/scopeData.ts#L142-L143)), so the device-context integration then copies the native user, installation ID included.

**Both native SDKs write the installation ID to a file on the device as soon as they start, whatever Cup does.** Android writes `files/INSTALLATION` on the first `Installation.id(context)` call ([`Installation.java` L36–L45](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry-android-core/src/main/java/io/sentry/android/core/Installation.java#L36-L45)), which init makes when it sets the distinct ID and which every event makes for the device context. Cocoa caches it asynchronously when the client starts ([`SentryClient.m` L182–L184](https://github.com/getsentry/sentry-cocoa/blob/61e8cb02434b26fb34c58126d883e5663cfde238/Sources/Sentry/SentryClient.m#L182-L184)) and writes `INSTALLATION` in the cache directory ([`SentryInstallation.swift` L18–L41](https://github.com/getsentry/sentry-cocoa/blob/61e8cb02434b26fb34c58126d883e5663cfde238/Sources/Swift/Helper/SentryInstallation.swift#L18-L41)). Neither SDK has an option to skip it. This conflicts with #341 decision 1, which keeps the ePrivacy line by "storing no telemetry-only identifier on the device". Keeping native crash capture therefore needs an operator decision on that file, separate from what reaches Sentry.

**Recommendation for the spec**, assuming the operator keeps native crash capture and accepts the `INSTALLATION` file (otherwise see [Alternative: JS only in the shells](#alternative-js-only-in-the-shells)):

1. **Organization scrubbing rule** (API, not Terraform), one rule set covering every project: remove `$user.geo.city || $user.geo.subdivision || $user.geo.region` and `contexts.device.id`. Optionally, as a backstop for native events captured before the JS user is set, remove `$user.id` values matching the installation ID formats, which differ from Cup's account IDs (see [Installation ID formats](#installation-id-formats)).
2. **Always set a user with an `id`** from JS: the account ID when signed in, and a constant placeholder such as `signed-out` otherwise, never `setUser(null)` or `setUser({})`. This is the only client-side lever that suppresses the installation ID on Android native events, and it keeps the native scope user non-empty on iOS.
3. **JS `beforeSend`** (and `beforeSendTransaction`) in the shells: delete `contexts.device.id`, keep `user` to `{ id }` from Cup's own state, and set `user.ip_address` to null as today.
4. **Turn off native session tracking in the shells**, which needs a one-line `pnpm patch` of `@sentry/capacitor` (see [Session tracking cannot be turned off from JS](#session-tracking-cannot-be-turned-off-from-js)), unless the operator accepts the installation ID as session `did`. Relay hashes `did` into a set metric and does not store it raw ([`sessions/mod.rs`](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-server/src/metrics_extraction/sessions/mod.rs#L16-L26), [`bucket.rs` L230–L232](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-metrics/src/bucket.rs#L230-L232)), but the raw ID still leaves the device. The cost is release health for the shells: crash-free sessions and users, and adoption.
5. **Optionally, point the shells' DSN at the Worker** so that native envelopes go through Cup's relay too and Sentry never sees the device's IP (see [Routing native envelopes through the Worker](#routing-native-envelopes-through-the-worker)). The scrubbing rule already removes city-level geo without it; this step is what #341 decision 5's "stripped in the relay before export" asks for literally, and it costs a forwarder route on the Worker.

## Candidate 1: a JS fetch transport through the tunnel

`@sentry/capacitor` uses the native transport only when the caller passes no `transport` ([`sdk.ts` L50–L61](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/src/sdk.ts#L50-L61)). Two ways out follow from that code:

- **`transport: makeFetchTransport` with `enableNative` left on.** The native SDK still starts and captures native crashes, but JS envelopes go through `@sentry/browser`'s fetch transport. The browser client builds the transport URL from `tunnel` ([`client.ts` L246–L250](https://github.com/getsentry/sentry-javascript/blob/042e228984d2d11fecc1de849c59bfbe8a1c42af/packages/core/src/client.ts#L246-L250)), so JS events take the tunnel and arrive with country-level geo only. Costs: JS errors no longer mark the native session errored or crashed, because only `NATIVE.sendEnvelope` runs `InternalSentrySdk.captureEnvelope`, which updates the session ([`InternalSentrySdk` L167–L205](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry-android-core/src/main/java/io/sentry/android/core/InternalSentrySdk.java#L167-L205)); JS envelopes lose the native SDK's disk cache and retry while offline; native events still go straight to Sentry with city geo and the installation ID. The device-context integration still runs (it depends on `enableNative`, [`default.ts` L24–L26](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/src/integrations/default.ts#L24-L26)), so JS events still need the `beforeSend` cleanup.
- **`enableNative: false`.** See the [alternative](#alternative-js-only-in-the-shells) below.

With CapacitorHttp enabled, the fetch transport's request itself goes out through Capacitor's native HTTP client, which does not change where it is sent. The SDK patches Capacitor's XHR for breadcrumbs on native platforms ([`sdk.ts` L67–L69](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/src/sdk.ts#L67-L69)); whether the tunnel request goes through cleanly is _unverified_.

A JS transport alone does not answer the question, since native crashes keep both problems. It is worth it only if Cup also wants JS events to keep the tunnel's IP stripping, and then the DSN route below covers native events as well.

### Alternative: JS only in the shells

`enableNative: false` keeps the native SDK from starting: `initNativeSdk` returns before calling the plugin ([`wrapper.ts` L110–L134](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/src/wrapper.ts#L110-L134)), the scope is not synced, and the device-context integration is replaced by the browser HTTP context. JS sessions come back through `browserSessionIntegration`, which is added only when native is off ([`default.ts` L43–L45](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/src/integrations/default.ts#L43-L45)); a JS session's `did` comes from the JS user, not from a device ID. Everything goes through the tunnel as on the web: no `INSTALLATION` file, no installation ID, no city geo, no device IP at Sentry.

What it costs: crashes outside the WebView (Java, Kotlin, Objective-C or Swift, including in Capacitor plugins), Android ANRs, iOS app hangs and watchdog terminations are no longer reported; offline events are dropped unless Cup adds `makeBrowserOfflineTransport`, which keeps queued events in IndexedDB (event data, not an identifier); native device and OS contexts disappear, leaving what the WebView's user agent gives. Since all of Cup's app logic is in the WebView, the lost crashes are those of the shell, its plugins and the WebView host. This is the only option that fully meets #341 decision 1 as written.

## Candidate 2: native-side options

**Cup cannot configure the native SDK beyond the options the plugin forwards.** The plugin calls `SentryAndroid.init` and `SentrySDK.start` itself, and forwards only the primitive options listed in `FilterNativeOptions` ([`nativeOptions.ts` L18–L51](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/src/nativeOptions.ts#L18-L51)). Both plugins install their own native `beforeSend`, which only tags the event origin ([Android L139–L145](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/android/src/main/java/io/sentry/capacitor/SentryCapacitor.java#L139-L145), [iOS L78–L82](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/ios/Sources/SentryCapacitorPlugin/SentryCapacitorPlugin.swift#L78-L82)). A native `beforeSend` would work in principle, since both SDKs run it after the processors that add the installation ID (Android [`SentryClient.java` L157–L160](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry/src/main/java/io/sentry/SentryClient.java#L157-L160); Cocoa sets the ID at [L1086](https://github.com/getsentry/sentry-cocoa/blob/61e8cb02434b26fb34c58126d883e5663cfde238/Sources/Sentry/SentryClient.m#L1086) and runs `beforeSend` at [L1136](https://github.com/getsentry/sentry-cocoa/blob/61e8cb02434b26fb34c58126d883e5663cfde238/Sources/Sentry/SentryClient.m#L1136)), but reaching it means patching the plugin's Java and Swift. It also cannot change the IP Relay sees, so it does not help with geo, except by pre-filling `user.geo`, which the bridge cannot carry.

**`sendDefaultPii` is already off, and no native SDK sends `{{auto}}` with it off.** Android adds `{{auto}}` only when user info collection is on ([`DefaultAndroidEventProcessor` L180–L182](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry-android-core/src/main/java/io/sentry/android/core/DefaultAndroidEventProcessor.java#L180-L182)). Cocoa sends `sdk.settings.infer_ip: "never"` when `sendDefaultPii` is off ([`SentrySDKSettings.swift` L27](https://github.com/getsentry/sentry-cocoa/blob/61e8cb02434b26fb34c58126d883e5663cfde238/Sources/Swift/Protocol/SentrySDKSettings.swift#L27)). None of this matters for geo, because the lookup falls back to the connection IP either way (see [How Relay decides on geo](#how-relay-decides-on-geo)).

**Neither native SDK has a `tunnel` option; the endpoint is derived from the DSN.** sentry-java posts to the DSN's host and path plus `api/{project}/envelope/` with an `X-Sentry-Auth` header ([`Dsn.java` L95–L101](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry/src/main/java/io/sentry/Dsn.java#L95-L101), [`RequestDetailsResolver.java` L40–L60](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry/src/main/java/io/sentry/RequestDetailsResolver.java#L40-L60)), and sentry-cocoa appends `envelope/` to the DSN's base endpoint ([`SentryDsn.swift` L91–L99](https://github.com/getsentry/sentry-cocoa/blob/61e8cb02434b26fb34c58126d883e5663cfde238/Sources/Swift/SentryDsn.swift#L91-L99)). A DSN whose host is Cup's Worker therefore routes all native traffic to the Worker. The plugin passes the one `dsn` to both layers, so JS envelopes sent through native follow too.

### Routing native envelopes through the Worker

With a DSN like `https://<public key>@<cup host>/<prefix>/<project id>`, both native SDKs post to `https://<cup host>/<prefix>/api/<project id>/envelope/`. The Worker forwards the body and the `X-Sentry-Auth` header to the real ingest URL `https://o<org id>.ingest.de.sentry.io/api/<project id>/envelope/`, without any client-IP header. Relay then sees Cloudflare's egress IP, as for the tunnel today: country-level geo only, and the device's IP never reaches Sentry.

`handleTunnelRequest` cannot do this forward. It reads the target from the `dsn` field of the envelope header and rejects envelopes without one ([`tunnelForward.ts` L336–L369](https://github.com/getsentry/sentry-javascript/blob/8bebd2951dc1ae1fb9406c51cb3f0b2332f9575e/packages/core/src/utils/tunnelForward.ts#L336-L369)); sentry-java's envelope header has only `event_id`, `sdk`, `trace` and `sent_at` ([`SentryEnvelopeHeader.java` L85–L88](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry/src/main/java/io/sentry/SentryEnvelopeHeader.java#L85-L88)), and a `dsn` naming the Worker would loop back to it. Cup needs a small forwarder with a fixed upstream that strips the same headers its tunnel strips. A web build could use the same DSN and drop `tunnel`, since the browser SDK sends to the same path with the key in the query string.

Side effects: the SDKs read the organization ID from a DSN host like `o123.ingest…` ([`SentryDsn.swift` L101–L107](https://github.com/getsentry/sentry-cocoa/blob/61e8cb02434b26fb34c58126d883e5663cfde238/Sources/Swift/SentryDsn.swift#L101-L107)), so `orgId` must be set explicitly for strict trace continuation; it is a forwarded option ([`nativeOptions.ts` L46](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/src/nativeOptions.ts#L46)). If the Worker is down, the native SDKs keep envelopes on disk and retry, as they would for Sentry. The forwarder can also rewrite envelope items (remove `contexts.device.id`, a leftover installation-ID `user.id`, or `did`), at the price of parsing and re-framing envelopes; the scrubbing rule does the first two without that.

## Candidate 3: server side

### How Relay decides on geo

`normalize_ip_addresses` fills `user.ip_address` from the connection only when it is `{{auto}}`, when the SDK sets `infer_ip: auto`, or, for legacy SDKs on platform `javascript`, `cocoa` or `objc`, when it is absent ([`event.rs` L424–L505](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-event-normalization/src/event.rs#L424-L505)), and with IP scrubbing on Relay passes it no client IP at all ([L282](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-event-normalization/src/event.rs#L282)). The geo lookup is separate: it uses `user.ip_address` unless that is `{{auto}}`, and otherwise `config.client_ip`, which is never filtered ([L296–L298](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-event-normalization/src/event.rs#L296-L298), [L508–L528](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-event-normalization/src/event.rs#L508-L528)). So null, absent and `{{auto}}` all lead to a lookup of the connection IP; only an explicit IP in the payload changes which IP is looked up.

The lookup is skipped when the event already has `user.geo` ([L513–L517](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-event-normalization/src/event.rs#L513-L517)), and `{}` parses to a present, empty `Geo` ([`user.rs` L121–L132](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-event-schema/src/protocol/user.rs#L121-L132)). Setting `user.geo = {}` in JS `beforeSend` could therefore block the lookup for JS events. It is not recommended: `user.geo` is skipped when empty on serialization ([`user.rs` L67–L69](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-event-schema/src/protocol/user.rs#L67-L69)), so a Relay hop that re-serializes the event before the processing Relay drops it, and native events cannot carry it at all.

Spans and logs, which Relay processes as EAP items, have their own path: geo comes only from a `client.address` attribute ([`eap/mod.rs` L430–L470](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-event-normalization/src/eap/mod.rs#L430-L470)), which Relay fills from the connection only for `{{auto}}` or when the SDK asks for IP inference ([`spans/process.rs` L284–L289](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-server/src/processing/spans/process.rs#L284-L289)). Logs get no geo lookup.

### The scrubbing rule

Sentry documents the selector form `[Remove] [Anything] from [$user.geo.**]` ([server-side scrubbing](https://docs.sentry.io/security-legal-pii/scrubbing/server-side-scrubbing/#geographic-information)); the [Advanced Data Scrubbing](https://docs.sentry.io/security-legal-pii/scrubbing/advanced-datascrubbing/) page describes selectors and the `||` operator, and the [event PII fields](https://docs.sentry.io/security-legal-pii/scrubbing/server-side-scrubbing/event-pii-fields/) list `user.geo.city`, `country_code`, `region` and `subdivision`. As `relayPiiConfig`, using Relay's built-in `@anything:remove` rule ([`builtin.rs` L73](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-pii/src/builtin.rs#L73)):

```json
{
  "applications": {
    "$user.geo.city || $user.geo.subdivision || $user.geo.region": ["@anything:remove"],
    "contexts.device.id": ["@anything:remove"]
  }
}
```

`contexts.device.id` is not a schema field; it lands in the device context's additional properties, which are `pii = "maybe"` ([`device.rs` L178–L180](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-event-schema/src/protocol/contexts/device.rs#L178-L180)). Relay skips only `pii = "false"` values ([`processor.rs` L63–L66](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-pii/src/processor.rs#L63-L66)), and an explicit path selector reaches `maybe` fields.

**One gap in transactions.** Normalization copies `user.geo.city`, `region` and `subdivision` into each child span's `sentry_tags` ([`event.rs` L363–L370](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-event-normalization/src/event.rs#L363-L370), [`tag_extraction.rs` L352–L373](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-event-normalization/src/normalize/span/tag_extraction.rs#L352-L373)) before scrubbing. Those tag fields carry no `pii` attribute ([`span.rs` L339–L348](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-event-schema/src/protocol/span.rs#L339-L348)), so the rule cannot remove them. The segment span is rebuilt from the scrubbed event ([`extraction.rs` L13–L23](https://github.com/getsentry/relay/blob/d46ae1fd35be2f701d9c4876b9de384dfee04e50/relay-server/src/processing/transactions/extraction.rs#L13-L23)), but whether child spans keep the pre-scrub city is _unverified_. This matters only if the shells send transactions; routing them through the Worker avoids it, since Relay then only ever sees Cloudflare's IP.

No project or organization setting other than this rule stops the lookup. Sentry's own `geo_by_addr` is used for account sign-in history, not for events ([`sentry/utils/geo.py`](https://github.com/getsentry/sentry/blob/73b55402452d544d70f534b457f66b84336743e9/src/sentry/utils/geo.py)).

### Installation ID formats

The Android ID is a UUID without dashes in lowercase hex (`SentryUUID.generateSentryId`, [`SentryUUID.java` L16–L18](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry/src/main/java/io/sentry/SentryUUID.java#L16-L18)); the iOS ID is `UUID().uuidString`, dashed and uppercase ([`SentryInstallation.swift` L27](https://github.com/getsentry/sentry-cocoa/blob/61e8cb02434b26fb34c58126d883e5663cfde238/Sources/Swift/Helper/SentryInstallation.swift#L27)). Cup's account IDs are `crypto.randomUUID()`, dashed and lowercase ([`registry-durable-object.ts` L121](../../libs/registry/src/durable-object/registry-durable-object.ts#L121)). A case-sensitive regex rule on `$user.id`, `^[0-9a-f]{32}$|^[0-9A-F]{8}-[0-9A-F]{4}-[0-9A-F]{4}-[0-9A-F]{4}-[0-9A-F]{12}$`, would remove installation IDs and keep account IDs. It is a backstop only, because it depends on formats neither SDK documents.

## Candidate 4: an explicit user

- **iOS:** any native user stops the installation ID on native events, since Cocoa checks `event.user == nil` ([`SentryClient.m` L1294](https://github.com/getsentry/sentry-cocoa/blob/61e8cb02434b26fb34c58126d883e5663cfde238/Sources/Sentry/SentryClient.m#L1294)). `Sentry.setUser({})` reaches native as an empty `User()` ([iOS `setUser`](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/ios/Sources/SentryCapacitorPlugin/SentryCapacitorPlugin.swift#L396-L413)). In 9.28.0 the `SDK_V10` branch, which would skip the ID with user info collection off, is not compiled in.
- **Android:** only a user with a non-null `id` stops it ([`DefaultAndroidEventProcessor` L176–L179](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry-android-core/src/main/java/io/sentry/android/core/DefaultAndroidEventProcessor.java#L176-L179)); `ApplicationExitInfoEventProcessor`, which reports ANRs and native crashes from an earlier run, does the same ([L685–L697](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry-android-core/src/main/java/io/sentry/android/core/ApplicationExitInfoEventProcessor.java#L685-L697)).
- **No option disables it** on either platform. `distinctId` (Android) and the session ID (iOS) are not forwarded options, and setting them would not change `user.id` or the device context.

So the portable choice is a user with an `id` at all times: the account ID, or a constant placeholder when signed out. A placeholder makes Sentry count every signed-out installation as one user, which is acceptable because Cup does not want per-device counts. Native events captured between native init and the first `setUser` call can still carry the installation ID; the regex rule covers that window.

## Session tracking cannot be turned off from JS

`enableAutoSessionTracking` is not in `FilterNativeOptions` ([`nativeOptions.ts` L18–L51](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/src/nativeOptions.ts#L18-L51)), so `Sentry.init({ enableAutoSessionTracking: false })` never reaches native, although both plugins would read it ([Android L112–L114](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/android/src/main/java/io/sentry/capacitor/SentryCapacitor.java#L112-L114), [iOS L133–L135](https://github.com/getsentry/sentry-capacitor/blob/a40c2c56339c4e3828e2f1913d1425f7e4ce4fc7/ios/Sources/SentryCapacitorPlugin/SentryCapacitorPlugin.swift#L133-L135)). `enableNativeCrashHandling` is missing from the list in the same way. On Android, the manifest key `io.sentry.auto-session-tracking.enable` works, because the manifest is read before the plugin's callback and the plugin leaves the option alone when it is not passed ([`ManifestMetadataReader.java` L71](https://github.com/getsentry/sentry-java/blob/683908daaa63add97ca9a1710ab4a6898ada1c2b/sentry-android-core/src/main/java/io/sentry/android/core/ManifestMetadataReader.java#L71)). iOS has no such file, so the clean fix for both is a `pnpm patch` adding `enableAutoSessionTracking: options.enableAutoSessionTracking` to `FilterNativeOptions`, and reporting it upstream.

## Needs hands-on confirmation

- **The scrubbing rule on shell events**: with the `relayPiiConfig` above set on the organization, an Android and an iOS JS error, a native crash on each, and a web event through the tunnel all show `user.geo` with `country_code` only and no `contexts.device.id`.
- **`setUser({ id })` on native crashes**: an Android native crash and an iOS crash after `Sentry.setUser({ id: 'signed-out' })` show that ID, not the installation ID, including an Android ANR reported on the next launch.
- **The `$user.id` regex rule** removes a planted Android-format and iOS-format ID and keeps a lowercase dashed UUID.
- **The session patch**: with `enableAutoSessionTracking` forwarded and set to false, no session envelopes leave either shell (watch with `debug: true` or a throwaway DSN pointed at a request bin under Cup's control).
- **Child span geo in transactions**: if the shells send transactions, whether child spans in the trace view still carry `user.geo.city` after the rule.
- **The Worker DSN route**, if chosen: both native SDKs accept a DSN with a path prefix and post to it; Sentry accepts the forwarded envelopes, including JS envelopes whose header `dsn` names the Worker; the stored geo is Cloudflare's country.
- **`transport: makeFetchTransport` in the shells**, if chosen: JS events reach the tunnel with CapacitorHttp enabled, and native crashes are still captured.
- **The `INSTALLATION` file**: confirm it appears in the app's files directory (Android) and cache directory (iOS) after the first launch, for the operator's decision against #341 decision 1.
