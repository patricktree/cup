# Mobile E2E tools for the Capacitor shells

Research date: 2026-11-06, for [issue #180](https://github.com/patricktree/cup/issues/180) of the [mobile QA map](https://github.com/patricktree/cup/issues/179). Repository observations are from `main` at `626776ac`. Tool versions are the latest releases on the research date: Appium `3.9.0` (stable, 2026-10-27) and `4.0.0-beta.7` (2026-10-31), UiAutomator2 driver `9.0.1`, XCUITest driver `13.0.7`, WebdriverIO `10.2.0`, Maestro CLI `2.12.1`, Playwright `1.65.0`. GitHub sources are cited at these commits: `appium/appium-uiautomator2-driver` `262c6f3a`, `appium/appium-xcuitest-driver` `cd2efd3f`, `mobile-dev-inc/maestro` `aaa248d7`, `mobile-dev-inc/maestro-docs` `664ad589`, `microsoft/playwright` `58d69dcc`, `webdriverio/webdriverio` `0082ce8a`. Nothing was installed or run against an emulator or simulator: every capability below is read from documentation or source, and the points marked _unverified_ need a prototype.

## Question

Which tools can drive both the native UI and the WebView content of Cup's Capacitor 8 shells on an Android emulator and an iOS simulator? The ticket compares Appium (UiAutomator2 and XCUITest drivers through WebdriverIO), Maestro, Playwright's Android support, and native XCUITest/Espresso, on system UI reach, DOM access in the WebView, TypeScript, 2026 maturity, pnpm monorepo fit, determinism under Cup's no-retry rule, and Mac install needs. A scope addition asks what Apple and Google officially recommend.

## Answer

Appium through WebdriverIO is the only option that reaches system UI on both platforms, gives real DOM access (CSS selectors, `execute`) inside the WebView on both platforms, and is written in TypeScript. Maestro reaches system UI on both platforms but sees the WebView only through the accessibility tree, and its flows are YAML with a sandboxed JavaScript engine. Playwright's Android support has the best WebView API but is experimental and has no iOS. The official frameworks (Espresso, Espresso-Web and UI Automator on Android; XCTest UI automation on iOS) have the highest fidelity for system UI, but they mean Kotlin and Swift suites, and XCTest has no DOM access.

## What Apple and Google recommend

### Apple

Apple's [Testing](https://developer.apple.com/documentation/xcode/testing) page names Swift Testing for unit tests and "XCTest to facilitate writing UI tests that control your app's UI using XCUIAutomation". It asks for a test pyramid: many unit tests, fewer integration tests, and "UI tests to assert the correct behavior of common use cases". In [WWDC25 session 344](https://developer.apple.com/videos/play/wwdc2025/344/) Apple says "Accessibility is the underlying framework that powers UI automation", recommends accessibility identifiers as locators, and notes that automation "runs completely independently from your app".

For system UI and other apps, [`XCUIApplication(bundleIdentifier:)`](<https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/init(bundleidentifier:)>) "creates a proxy for an application for the specified bundle identifier" and launches an installed app such as Safari when the test scheme does not build it. [WWDC20 session 10220](https://developer.apple.com/videos/play/wwdc2020/10220/) covers alerts: XCTest implicitly handles interrupting elements with a cancel or default button, `addUIInterruptionMonitor` handles others, and `resetAuthorizationStatus(for:)` makes the app ask for a protected resource again. Apple documents nothing specific to testing Share Extensions.

For web content, XCUIAutomation offers only the [`webViews`](https://developer.apple.com/documentation/xcuiautomation/xcuielementtypequeryprovider/webviews) element query over the accessibility tree. DOM access goes through Safari Web Inspector, which a `WKWebView` allows when [`isInspectable`](https://developer.apple.com/documentation/webkit/wkwebview/isinspectable) is true (default `false`). Capacitor sets it for development builds when `ios.webContentsDebuggingEnabled` is unset ([Capacitor config](https://capacitorjs.com/docs/config)).

Test plans set "timeouts, repetitions, parallelization, execution order" (WWDC25 session 344). The repetition modes include "repeated until they pass" ([test plans](https://developer.apple.com/documentation/xcode/organizing-tests-to-improve-feedback)), which is a retry and must stay off under Cup's rules. `xcodebuild test` runs plans from the command line and writes an `.xcresult` bundle ([running tests](https://developer.apple.com/documentation/xcode/running-tests-and-interpreting-results)).

### Google

Google's [testing strategy](https://developer.android.com/training/testing/fundamentals/strategies) page also draws a pyramid: "Most apps should have many small tests and relatively few big tests", and it advises "the lowest layer of the pyramid that can give the team the right level of feedback". Its application layer tests a debuggable binary with mocked or staging services on emulators, which is the layer Cup's map describes. Its release-candidate layer, a minified build against production, matches what stays in CUP-44.

The [behavior UI tests](https://developer.android.com/training/testing/ui-tests/behavior) page assigns the frameworks: Espresso for "Views within a single target app" with automatic synchronization, Compose testing for Compose screens, and UI Automator "for cross-app functional UI testing across system and installed apps". The [UI Automator guide](https://developer.android.com/training/testing/other-components/ui-automator) recommends its 2.4 Kotlin API, which is still `2.4.0-alpha05` there, and shows `watchFor(PermissionDialog) { clickAllow() }` for permission dialogs. [Espresso-Web](https://developer.android.com/training/testing/espresso/web) is Google's tool for hybrid apps: it "reuses Atoms from the popular WebDriver API" and finds DOM elements by ID, CSS or XPath inside a `WebView`. Google does not mention Capacitor, Cordova or third-party E2E tools in these pages.

[Gradle Managed Devices](https://developer.android.com/studio/test/managed-devices) create, run and tear down emulators from Gradle and support sharding. Their Automated Test Device images remove Chrome, the Settings app and SystemUI, because tests should assume "other apps or the platform will function correctly"; a test of the real Sharesheet or a permission dialog therefore needs a full `google` image. The page points to [Espresso-Intents](https://developer.android.com/training/testing/espresso/intents) for stubbing outgoing intents instead.

### How third-party tools relate

All the third-party tools run on top of these frameworks rather than replacing them:

- The Appium UiAutomator2 driver forwards native commands to "appium-uiautomator2-server", which "trasforms API commands to appropriate low-level UiAutomator framework calls", and proxies web contexts to Chromedriver ([driver README, Hybrid Mode](https://github.com/appium/appium-uiautomator2-driver/blob/262c6f3a0c43f84f5087873e1ddaade2a33a1526/README.md#hybrid-mode)).
- The Appium XCUITest driver depends on WebDriverAgent, which "relies on Apple's XCTest framework" ([system requirements](https://github.com/appium/appium-xcuitest-driver/blob/cd2efd3fa4e58cf50a2b37dc38b2a2de5de9a635/docs/getting-started/system-requirements.md)), and reaches web content through the Web Inspector remote debugger, injecting Selenium atoms ([hybrid guide](https://appium.github.io/appium-xcuitest-driver/latest/guides/hybrid/)). The Android and iOS DOM paths are thus the same atom-based approach Espresso-Web uses.
- Maestro drives "the app through the platform's accessibility layer" ([README](https://github.com/mobile-dev-inc/maestro/blob/aaa248d7fd4ca4924444dc027af9c7a62a9be348/README.md)); its repository contains an Android instrumentation driver (`maestro-android/src/androidTest`) and an XCTest runner (`maestro-ios-xctest-runner`).
- Playwright installs a driver APK and starts it with `am instrument … AndroidJUnitRunner` on every run ([`android.ts`](https://github.com/microsoft/playwright/blob/58d69dcc392af3a6994eab0323dc2e883f05f396/packages/playwright-core/src/server/android/android.ts)); the driver uses UI Automator's `UiDevice`.

So the tools' system UI reach is bounded by UI Automator and XCTest, and their iOS DOM reach is bounded by Web Inspector. A Share Extension step that XCTest cannot reach is unreachable for Appium and Maestro too.

## Cup's surface under test

- Android declares an `ACTION_SEND` `text/plain` intent filter on `MainActivity`, which is `singleTask` ([`AndroidManifest.xml`](../../apps/mobile-app/android/app/src/main/AndroidManifest.xml)). The manifest requests only `INTERNET`, so no runtime permission dialog, including `POST_NOTIFICATIONS`, exists yet; one appears when native playback lands with [CUP-41](https://linear.app/cup-audio/issue/CUP-41/android-and-ios-apps-that-play-the-narration-track).
- [`capacitor.config.ts`](../../apps/mobile-app/capacitor.config.ts) enables the App plugin's back-button handler; the web side is [`back-button.android.ts`](../../apps/web-app/src/platform/back-button.android.ts). It sets no `webContentsDebuggingEnabled`, so only debug builds have an inspectable WebView (Capacitor config: Android debugging "is automatically enabled during development"; iOS "it's `true` for development builds"). Every DOM-capable tool here therefore tests debug builds.
- iOS hands off from `CupShare` through `audio.cup.app://share?url=…` ([mobile README](../../apps/mobile-app/README.md#ios-share-extension)).
- Android Google sign-in runs through `@capawesome/capacitor-google-sign-in` ([`package.json`](../../apps/mobile-app/package.json)), which shows Google's own account UI and needs a real account; the map rules real accounts out, so that sheet is out of reach for every tool and a fake is needed instead.

## Appium with WebdriverIO

### Maturity

Appium's stable line is 3.x (`appium@3.9.0`, 2026-10-27, Apache-2.0). Appium 4 has been in beta since 2026-09-19 (`4.0.0-beta.0` to `beta.7`). The newest driver majors already require it: UiAutomator2 driver 9.0.0 (2026-11-01) "requires Appium >=4.0.0-beta.0" and drops Node 20, and the XCUITest driver's compatibility table maps 13.x to Appium 4 and 10.0.0–12.22.8 to Appium 3 ([system requirements](https://github.com/appium/appium-xcuitest-driver/blob/cd2efd3fa4e58cf50a2b37dc38b2a2de5de9a635/docs/getting-started/system-requirements.md#driver-to-appium-server)). A suite started now would pin Appium 3 with UiAutomator2 8.x and XCUITest 12.x and plan one migration, or start on the Appium 4 beta. The XCUITest driver aims to fully support only the latest two major Xcode and iOS versions.

WebdriverIO 10.0.0 shipped on 2026-10-05; `10.2.0` is from the research date. It is TypeScript-first, and its [`switchContext`](https://webdriver.io/docs/api/mobile/switchContext/) command selects a WebView by `title` or `url` and handles Android's two-step context and page switch.

### System UI

UiAutomator2 sends intents with [`mobile: startActivity`](https://github.com/appium/appium-uiautomator2-driver/blob/262c6f3a0c43f84f5087873e1ddaade2a33a1526/README.md#mobile-startactivity) (action, MIME type, string extras), which covers Cup's `ACTION_SEND` intake without Chrome. Driving the real Sharesheet from Chrome is also possible because the native context is UiAutomator. The back button is [`mobile: pressKey`](https://github.com/appium/appium-uiautomator2-driver/blob/262c6f3a0c43f84f5087873e1ddaade2a33a1526/README.md#mobile-presskey) with keycode 4. Permissions use `appium:autoGrantPermissions` or [`mobile: changePermissions`](https://github.com/appium/appium-uiautomator2-driver/blob/262c6f3a0c43f84f5087873e1ddaade2a33a1526/README.md#mobile-changepermissions); to see the dialog itself, tap it in the native context. `mobile: shell` needs the server feature `uiautomator2:adb_shell`.

The XCUITest driver can bring Safari forward with `mobile: activateApp` and open URLs with [`mobile: deepLink`](https://github.com/appium/appium-xcuitest-driver/blob/cd2efd3fa4e58cf50a2b37dc38b2a2de5de9a635/docs/reference/execute-methods.md#mobile-deeplink) (Xcode 14.3+, iOS 16.4+), which can exercise the `audio.cup.app://share` handoff without the extension. Its `defaultActiveApplication` and `respectSystemAlerts` settings control which app's tree it reads. Alerts use `appium:autoAcceptAlerts` or `mobile: alert`; simulator privacy uses `appium:permissions` or `mobile: setPermission` (backed by `xcrun simctl privacy`, some services by `applesimutils`). Whether the `CupShare` row in Safari's Share Sheet and the extension's own button are reachable in WebDriverAgent's tree is _unverified_. In an August 2025 forum thread about Siri's response window ([796503](https://developer.apple.com/forums/thread/796503)), `XCUIApplication(bundleIdentifier:)` with system service bundle IDs found nothing, and Apple DTS answered that UI tests are not meant for "anything outside of your app's UI process that the system is displaying on behalf of your app"; the Share Sheet is such UI, so its reachability is a real risk.

### WebView

On Android, switching to a `WEBVIEW_*` context starts a Chromedriver and proxies WebDriver commands to it. "Google requires that the used Chromedriver version must always match" the WebView version; the driver can download a matching one when the server runs with `--allow-insecure uiautomator2:chromedriver_autodownload` ([Hybrid Mode](https://github.com/appium/appium-uiautomator2-driver/blob/262c6f3a0c43f84f5087873e1ddaade2a33a1526/README.md#hybrid-mode)), or a pinned binary is configured per emulator image. `mobile: getContexts` takes `waitForWebviewMs` because the devtools socket can fail to connect on Chrome 115 and later.

On iOS, the WebView must be inspectable and appear in Safari's remote debugger; then "the full Selenium WebDriver API is available" and commands run by "injecting Selenium atom scripts" ([hybrid guide](https://appium.github.io/appium-xcuitest-driver/latest/guides/hybrid/)). `appium:webviewConnectTimeout` (default 5000 ms) covers slow simulators. An opt-in `mobile: startAutomationSession` uses WebKit's automation protocol on simulators, but the guide warns that W3C Actions there can wedge the connection.

### Repository fit and concurrency

Appium keeps drivers in `APPIUM_HOME` (default `~/.appium`). Listing `appium` and drivers in a project's `package.json` works with npm only: "Other package managers are not currently supported" ([managing extensions](https://appium.io/docs/en/latest/guides/managing-exts/)). In a pnpm workspace the drivers would be installed with `appium driver install` into a repo-local, ignored `APPIUM_HOME`, pinned by a script. WebdriverIO, its Appium service and TypeScript tests are ordinary workspace dependencies.

Every host port is a capability: `appium:systemPort` (default first free in 8200–8299), `appium:chromedriverPort`, `appium:webviewDevtoolsPort` (10900–11000), `appium:mjpegServerPort`, and on iOS `appium:wdaLocalPort` (default 8100) and a unique `appium:derivedDataPath` ([parallel tests](https://github.com/appium/appium-xcuitest-driver/blob/cd2efd3fa4e58cf50a2b37dc38b2a2de5de9a635/docs/guides/parallel-tests.md)). The defaults search fixed ranges rather than asking the OS, so Cup's rule means allocating free ports in the test setup and passing them in. The WebdriverIO Appium service starts its own server and uses `getPort({ port: 4723 })` when no port is set ([`launcher.ts`](https://github.com/webdriverio/webdriverio/blob/0082ce8a0bbb50a974e55eaad7458fe3cb9a73ac/packages/wdio-appium-service/src/launcher.ts)), so it prefers 4723 but takes another free port if that is busy.

### Determinism

Neither Appium nor WebdriverIO retries by default. The known sources of flakiness are environmental: a Chromedriver that does not match the WebView, WebView contexts that appear late (bounded by `waitForWebviewMs`, `webviewConnectTimeout` and `switchContext` timeouts), and WebDriverAgent build and startup time on iOS. Pinning the emulator image, the simulator runtime and Chromedriver removes the first.

### Mac install

Android Studio with SDK and an emulator image, `ANDROID_HOME` and `JAVA_HOME` set (both required by the UiAutomator2 driver), Xcode with an iOS simulator runtime, Node (already required), the Appium drivers, and a Chromedriver matching the emulator's WebView. WebDriverAgent is built by `xcodebuild` on the first session unless a prebuilt one is supplied.

## Maestro

Maestro is Apache-2.0, released every few weeks (CLI 2.0.0 on 2025-08-26, 2.12.1 on 2026-11-02), and runs on emulators, simulators and physical Android devices; "Physical iOS devices are not yet supported" ([README](https://github.com/mobile-dev-inc/maestro/blob/aaa248d7fd4ca4924444dc027af9c7a62a9be348/README.md)). It names Ionic and hybrid apps as supported.

System UI: `back` (Android and web only), `setPermissions` on both platforms, including `notifications`, and taps on any element in the accessibility tree, which includes system dialogs and other apps. No command documented on the research date sends an Android intent with extras, so share intake would be driven through a sharing app's UI or an `adb` call outside the flow. Reaching `CupShare` from Safari is _unverified_, with the same XCTest limits as above.

WebView: Maestro sees web content only as accessibility nodes; when that fails, its [known issues](https://github.com/mobile-dev-inc/maestro-docs/blob/664ad5890b4d422341c80e401e349a5e4ab8c5a0/resources/troubleshooting/known-issues.md) page suggests `androidWebViewHierarchy: devtools`, which builds the Android hierarchy through Chrome DevTools. There is no iOS equivalent and no CSS selector or in-page script: JavaScript runs "in a restricted sandbox" on GraalJS, outside the app ([JavaScript overview](https://github.com/mobile-dev-inc/maestro-docs/blob/664ad5890b4d422341c80e401e349a5e4ab8c5a0/flows/javascript/javascript-overview.md)).

TypeScript and repository fit: flows are YAML; the CLI is a Java program installed by `curl … | bash` or Homebrew and needs Java 17+ with `JAVA_HOME` ([install guide](https://github.com/mobile-dev-inc/maestro-docs/blob/664ad5890b4d422341c80e401e349a5e4ab8c5a0/maestro-cli/how-to-install-maestro-cli/README.md)). Nothing installs through pnpm; a package script would call a CLI on `PATH`, and its version could not be pinned by the lockfile.

Concurrency and determinism: Maestro connects to its on-device drivers on fixed host ports, 7001 for Android (`DEFAULT_DRIVER_HOST_PORT`) and 22087 for iOS (`defaultXcTestPort` in [`MaestroSessionManager.kt`](https://github.com/mobile-dev-inc/maestro/blob/aaa248d7fd4ca4924444dc027af9c7a62a9be348/maestro-cli/src/main/java/maestro/cli/session/MaestroSessionManager.kt)). The override `--driver-host-port` is declared `hidden = true` in [`App.kt`](https://github.com/mobile-dev-inc/maestro/blob/aaa248d7fd4ca4924444dc027af9c7a62a9be348/maestro-cli/src/main/java/maestro/cli/App.kt), so two checkouts running at once would collide unless they pass an undocumented flag. Maestro advertises "built-in flakiness tolerance and automatic waiting"; that is command-level waiting, not test retries, but it is not configurable per suite and can hide timing regressions that Cup's no-retry rule is meant to surface.

## Playwright Android

Playwright has "experimental support for Android automation" of Chrome and Android WebView ([`Android`](https://playwright.dev/docs/api/class-android)); the API is exported as `_android`, and there is no iOS counterpart. It needs adb, and on non-rooted devices Chrome 105+ with command-line flags enabled for Chrome itself. `device.webView({ pkg })` returns a WebView with a full Playwright `Page`, the richest DOM API of all options. Native control goes through `AndroidSelector` on [`AndroidDevice`](https://playwright.dev/docs/api/class-androiddevice) (`tap`, `fill`, `press` with `AndroidKey` `'Back'`) and `device.shell()` for `am start` intents and `pm grant`. The docs warn that not all tests were run against devices, so some features may not work. Development continues: a 2026-08-28 commit replays execution contexts when connecting to Android WebView, and a 2026-10-08 commit passes call timeouts to the driver.

Repository fit is the best of all options, since `@playwright/test` `1.64.0` is already in the catalog ([`pnpm-workspace.yaml`](../../pnpm-workspace.yaml)) and tests are TypeScript. One mismatch: `qa/e2e` runs browsers in the shared Playwright Server container, while `_android.devices()` talks to an adb server at `127.0.0.1:5037`, so Android tests would run Playwright on the host. Install needs only `playwright install android` for the driver APKs. The adb server is shared across checkouts by design; the driver is reinstalled on every run, which would conflict if two checkouts drove the same emulator, but not on separate emulators.

## Native XCUITest and Espresso

These are the frameworks Apple and Google recommend, described above. On Android, one instrumentation suite can combine UI Automator for the Sharesheet, permissions and back, Espresso-Web for the DOM, and Espresso-Intents for intent assertions, run by Gradle Managed Devices that own the emulator lifecycle. On iOS, a UI test target can drive Safari, the Share Sheet and `CupShare` through `XCUIApplication(bundleIdentifier:)` and handle alerts, but it can assert on WebView content only through accessibility labels, not the DOM.

Costs: two suites in Kotlin and Swift beside a TypeScript codebase, sharing no helpers with `qa/e2e`; the iOS suite needs a UI test target added to [`App.xcodeproj`](../../apps/mobile-app/ios/App/App.xcodeproj), and the Android suite needs `androidTest` dependencies (the Capacitor template already declares `androidxEspressoCoreVersion` in [`variables.gradle`](../../apps/mobile-app/android/variables.gradle)). Mac install is nothing beyond Android Studio, Java 21 and Xcode, which mobile development already needs. Determinism is the strongest of all options: Espresso synchronizes with the main thread, and no test runs through a remote WebDriver hop.

## Recommendation

Use Appium through WebdriverIO, in a new TypeScript workspace package beside `qa/e2e`, with the UiAutomator2 and XCUITest drivers. It is the one tool that meets the map's needs on both platforms, it builds on the frameworks Apple and Google recommend, and it keeps the suite in the repository's language and package manager. Pin Appium 3.9 with UiAutomator2 8.x and XCUITest 12.x for now and record the Appium 4 migration as known work, since both drivers' newest majors already target the Appium 4 beta.

Constraints the spec should carry:

- Allocate every host port (Appium, `systemPort`, `chromedriverPort`, `webviewDevtoolsPort`, `wdaLocalPort`, `mjpegServerPort`) from the OS in test setup, and give each run its own emulator, simulator and `derivedDataPath`.
- Install drivers into a repo-local `APPIUM_HOME` from a pinned script, because Appium does not support pnpm for package-managed drivers.
- Pin the emulator system image (a full `google_apis` image, not ATD, so Chrome, SystemUI and dialogs exist) and the Chromedriver that matches its WebView; avoid runtime auto-download.
- Test debug builds, which are the only inspectable ones.
- Start share intake with an `ACTION_SEND` intent and the iOS handoff with `mobile: deepLink` for the deterministic cases, and keep one journey each through Chrome's Sharesheet and Safari's Share Sheet for the real system UI.
- Fake Google sign-in in the shell, since no tool can use Google's account sheet without a real account.

Before the spec commits to this, a prototype should confirm on Cup's own build that WebDriverAgent finds the `CupShare` row in Safari's Share Sheet and the extension's **Open in Cup** button, and that the Capacitor WebView context appears on both platforms. If the extension is unreachable for WebDriverAgent, a native XCUITest target is no better, because both read the same XCTest tree; that step would stay manual in CUP-44. Maestro is the fallback if the TypeScript and DOM requirements are dropped; Playwright Android is worth revisiting only if the Android suite needs Playwright's WebView API and iOS is covered another way.
