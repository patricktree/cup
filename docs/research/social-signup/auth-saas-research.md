## Follow-up requirement

On 2026-09-17 Patrick required native Google sign-in on Android and native Apple sign-in on iOS, excluding browser authentication for those paths. The [six-provider native integration research](native-social-sso-research.md) supersedes the integration-based recommendation below. In particular, the Auth0 Capacitor browser quickstart is not evidence that the native requirement is met.

## Recommendation for the decision

Compare **Auth0 and Supabase Auth** first. Auth0 has the clearest documented path for Cup's actual mobile stack; Supabase has more transparent, lower published MAU growth costs but needs more integration work. Keep Clerk as a third option if its React account UI is especially valuable and a Capacitor spike proves session handoff. None requires buying a billing or entitlements product. The comparisons below establish the evidence; the recommendation is an engineering judgment.

## Cloudflare first

I did not identify a documented Cloudflare-operated consumer identity service that meets this complete requirement. Cloudflare Access protects applications and integrates identity providers; its new Worker integration can expose authenticated identity through `ctx.access`, but this is not evidence of consumer signup, Google/Apple account linking, or a mobile customer-account lifecycle. Cloudflare's own identity provider authenticates existing Cloudflare account members. Do not equate “authentication on Workers” with a managed customer identity product. Sources: [Access product](https://www.cloudflare.com/products/access/), [Access on Workers](https://developers.cloudflare.com/workers/configuration/cloudflare-access/), [Access changelog](https://developers.cloudflare.com/cloudflare-one/changelog/access/).

Cloudflare integrations and partner deployments remain separate vendors: Cloudflare's documented Azure AD B2C partnership, for example, combines Cloudflare protection with Microsoft's identity service. Better Auth itself is an authentication framework, not a Cloudflare-managed identity service. Both categories differ from the requested SaaS model. Sources: [Cloudflare and Azure AD](https://www.cloudflare.com/static/f5889a43d596df139efd6e30773df7cb/Cloudflare_and_Azure_AD_Whitepaper.pdf), [Better Auth repository](https://github.com/better-auth/better-auth).

## Sessions, identity, and operations

### Auth0

Register web and native clients with explicit callback, logout, and origin allowlists; the Capacitor guide uses the Browser and App plugins and warns against persisting tokens in Capacitor Preferences because its backing stores are unencrypted. Secure persistent storage and app-restart behavior still need a design. A React Native SDK is not a substitute for this Capacitor integration. Source: [Capacitor guide](https://auth0.com/docs/quickstart/native/ionic-react).

Workers can verify Auth0 API JWTs with public signing keys; configure an API audience and validate issuer, audience, signature, and expiry. This is a compatibility inference from Auth0's JWT model and Workers Web Crypto, not a tested Cup integration. Sources: [token practices](https://auth0.com/docs/secure/tokens/token-best-practices), [API access tokens](https://auth0.com/docs/secure/tokens/access-tokens/get-access-tokens), [Workers Web Crypto](https://developers.cloudflare.com/workers/runtime-apis/web-crypto/).

Account linking requires an explicit implementation and authentication of the linked account; Auth0 warns that availability depends on plan and login implementation, and primary identity handling matters. Refresh-token revocation has configurable grant-wide behavior. User deletion is available through the Management API. Neither deleting Cup's local session nor deleting the Auth0 user should be assumed to revoke the upstream Apple grant. Sources: [linking](https://auth0.com/docs/manage-users/user-accounts/user-account-linking/link-user-accounts), [revocation](https://auth0.com/docs/api/authentication/revoke-refresh-token/revoke-refresh-token), [deletion](https://auth0.com/docs/manage-users/user-accounts/delete-users).

### Supabase Auth

Use asymmetric signing keys and the project's JWKS to validate tokens in the Worker; signing-key cache and rotation behavior are documented. Same-email identities can link automatically; authenticated manual linking also supports different emails. Apple relay email may differ from Google email, so shared email cannot be Cup's universal account key. Sources: [signing keys](https://supabase.com/docs/guides/auth/signing-keys), [identity linking](https://supabase.com/docs/guides/auth/auth-identity-linking).

Signout supports local/global/other-session scopes, but previously issued access JWTs remain valid until expiry. Admin user deletion requires a privileged server credential. Cup therefore needs a deliberate invalidation policy for private audiobook access, not an assumption that logout instantly revokes all JWTs. Local Auth can run through Supabase CLI/Docker; hosted social-provider configuration and callbacks still need real integration testing. Sources: [signout](https://supabase.com/docs/guides/auth/signout), [deleteUser](https://supabase.com/docs/reference/javascript/auth-admin-deleteuser), [local development](https://supabase.com/docs/guides/local-development).

### Clerk

Clerk attempts automatic linking on matching email with verification safeguards; different-email linking has a separate user flow. Its session JWTs last 60 seconds and are refreshed separately from the long-lived session, limiting rather than eliminating post-revocation JWT validity. Backend user deletion is supported. Sources: [linking](https://clerk.com/docs/guides/configure/auth-strategies/social-connections/account-linking), [session architecture](https://clerk.com/docs/guides/how-clerk-works/overview), [user management](https://clerk.com/docs/guides/users/managing).

A development instance and allowed Capacitor origins are only the beginning: an actual device must demonstrate provider login outside the WebView, callback delivery, session persistence, logout, and secure storage. This research has not verified those properties or a complete first-party Capacitor recipe. Clerk's production architecture also uses a configured frontend API subdomain. Sources: [origins](https://clerk.com/docs/reference/backend/instance/update), [architecture](https://clerk.com/docs/guides/how-clerk-works/overview).

## Google and Apple constraints

- Google forbids authorization inside an embedded user-agent controlled by the app. Use a suitable system authentication browser or native provider SDK, not the Capacitor app WebView. Production OAuth also needs appropriate registered origins/redirects and a public homepage with privacy-policy and terms links. Sources: [Google OAuth policy](https://developers.google.com/identity/protocols/oauth2/policies), [Google platform clients and WebViews](https://developers.googleblog.com/upcoming-security-changes-to-googles-oauth-20-authorization-endpoint-in-embedded-webviews/).
- Apple's login-services rule requires an equivalent privacy-preserving option when applicable third-party login is offered; Google plus Apple matches the user's chosen direction. Account creation also requires an in-app way to initiate account deletion. This expands the launch lifecycle beyond login/logout. Sources: [App Review Guidelines, 4.8 and 5.1.1](https://developer.apple.com/app-store/review/guidelines/), [account deletion guidance](https://developer.apple.com/support/offering-account-deletion-in-your-app).
- Apple account deletion includes revoking associated Sign in with Apple tokens. Deleting only the SaaS identity is not evidence this happens. Confirm the chosen vendor's token custody/revocation path. Source: [Apple account management](https://developer.apple.com/design/human-interface-guidelines/managing-accounts).
- Web/Android Apple OAuth needs Apple configuration: an App ID, associated Services ID, return URLs, signing key, and client secret. Supabase documents six-month Apple OAuth secret rotation, native Apple ID-token exchange, and that full name is only supplied on initial authorization and is not an ID-token claim. Prefer native Apple sign-in on iOS where practical; do not require a name to identify an account. Source: [Supabase Apple integration](https://supabase.com/docs/guides/auth/social-login/auth-apple).

## Decisions and evidence still needed

1. Select Auth0 versus Supabase (or justify the Clerk integration investment), including acceptable cost at expected active-user volumes and provider-linking requirements.
2. Prove the selected approach on both Capacitor platforms: initial signup, existing-account login, callback with app closed/open, cancellation, secure token storage, restart/refresh, and logout. No provisioning or prototype was performed here.
3. Choose Cup's stable internal account key and authenticated identity-linking behavior, particularly Apple private email; do not infer that two provider identities mean two humans or automatically award credits on every new linked identity.
4. Specify deletion/revocation across SaaS identity, upstream Apple grant, Cup account, private assets, and free-credit re-registration policy. Provider deletion APIs do not decide Cup's retention policy.
5. Specify private media authorization and its revocation bound independently from API authentication. A JWT-compatible SaaS does not itself protect existing public audio URLs.

The Cloudflare conclusion is a documented-product fit assessment, not proof that no relevant future/private product exists. Pricing is a dated snapshot. No vendor has been selected, services provisioned, paid APIs called, or Git branches created.
