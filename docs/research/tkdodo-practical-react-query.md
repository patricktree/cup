## Question

What do the 33 posts recommend on the topics the map decides: `staleTime` and `gcTime`, avoiding loading states on revisits, Suspense and `useSuspenseQuery`, prefetching and router loaders, query keys and invalidation after writes, `setQueryData` versus invalidation, polling, error handling for queries with cached data, and testing? Where does a recommendation conflict with `@tanstack/react-query` 5.104 or with the decisions in [issue #146](https://github.com/patricktree/cup/issues/146)?

## Answer

- **The series' model fits the map's rules.** Show cached data at once and refetch in the background (stale-while-revalidate); show a loading state only when there is no data; let the router start fetches early and let the Query cache own caching. The newest router post, [#32](https://tkdodo.eu/blog/tan-stack-router-and-query), describes almost exactly the decided setup: an awaited loader that primes the cache, `useSuspenseQuery` in the component, `defaultPreloadStaleTime: 0`, and the router's default boundaries.
- **The loader and the mount do not double fetch on a first visit, but only because of a Suspense detail.** [#32](https://tkdodo.eu/blog/tan-stack-router-and-query#combining-query-and-router) says the component finds the cached data or joins the in-flight request, so there is one request. With `staleTime: 0` that holds for `useSuspenseQuery` because suspense mode raises `staleTime` to at least 1,000 ms; with plain `useQuery` the mount after an awaited loader refetches. On a revisit, the cached data renders and the mount refetches once in the background, which is what decision 2 of #146 wants.
- **In the loader, use the `ensureQueryData` behaviour, not a plain `queryClient.query(options)`.** 5.104 deprecates `ensureQueryData` for `queryClient.query({ ...options, staleTime: 'static' })`. A plain `queryClient.query` with the client's `staleTime: 0` treats cached data as stale and awaits a network round trip in the loader on every revisit, holding the previous screen. The 2022 router post ([#16](https://tkdodo.eu/blog/react-query-meets-react-router#getquerydata--fetchquery)) makes the same point: return cached data, even stale, so revisits render instantly.
- **For a failed refetch of cached data, the series keeps the data on screen.** Check data before error ([#4](https://tkdodo.eu/blog/status-checks-in-react-query#background-errors)), and show a toast only for background failures from the global `QueryCache` `onError` ([#11](https://tkdodo.eu/blog/react-query-error-handling#putting-it-all-together)). Cup already does exactly this. `useSuspenseQuery` throws to the error boundary only when the query has no data, and it ignores a custom `throwOnError`, so decision 10 of #146 (show the error screen on _not found_ or _access denied_) needs code of its own.
- **Writes: invalidate by default, edit the cache only where needed.** This matches decision 4 of #146. Invalidation refetches only active queries and marks the rest stale ([#12](https://tkdodo.eu/blog/mastering-mutations-in-react-query#invalidation), [#25](https://tkdodo.eu/blog/automatic-query-invalidation-after-mutations#but-isnt-that-excessive)), so broad invalidation is cheap. A direct edit must cancel in-flight refetches first, or a refetch that started earlier overwrites it ([#29](https://tkdodo.eu/blog/concurrent-optimistic-updates-in-react-query#query-cancellation)). That matters for decision 6, because the account history polls every 5 seconds while a conversion is pending, so a history fetch can be in flight when the delete edits the cache.
- **Keys and factories:** generic-to-specific array keys with one factory per owner ([#8](https://tkdodo.eu/blog/effective-react-query-keys#use-query-key-factories)), later replaced by `queryOptions` factories that keep key and function together ([#24](https://tkdodo.eu/blog/the-query-options-api#query-factories)), with per-screen options added at the call site ([#31](https://tkdodo.eu/blog/creating-query-abstractions#composing-queryoptions)). This agrees with decision 5 of #146.
- **Where the series diverges from #146:** TkDodo rarely changes `gcTime` and prefers a non-zero `staleTime` (at least 20 seconds in [#10](https://tkdodo.eu/blog/react-query-as-a-state-manager#customize-staletime), about two minutes in [#25](https://tkdodo.eu/blog/automatic-query-invalidation-after-mutations#but-isnt-that-excessive)), while saying there is no correct value. He also advises against turning off the refetch triggers without a reason ([#10](https://tkdodo.eu/blog/react-query-as-a-state-manager#takeaways)); cup turns off `refetchOnWindowFocus` and `refetchOnReconnect`. Neither conflicts with a decision, but both are choices the series would question.
- **The series does not cover** how to poll a screen hidden in React `<Activity>`, nor how to test that no loading state appears. Its testing post ([#5](https://tkdodo.eu/blog/testing-react-query)) covers the basics only: a new `QueryClient` per test, retries off, Mock Service Worker, and awaiting results.

## Findings by topic

### `staleTime` and `gcTime`

- `staleTime` decides when data turns from fresh to stale; only stale data refetches on the triggers (mount, window focus, reconnect, key change). `gcTime` (named `cacheTime` before v5) decides how long a query without observers stays in the cache, 5 minutes by default. The author has rarely needed to change `gcTime`; `staleTime` is the setting to adjust ([#1](https://tkdodo.eu/blog/practical-react-query#the-defaults-explained)).
- The `staleTime: 0` default leans towards fresh data over fewer requests. There is no correct value; the talk ([#21](https://tkdodo.eu/blog/thinking-in-react-query)) suggests one global default overridden per query, and [#10](https://tkdodo.eu/blog/react-query-as-a-state-manager#customize-staletime) shows per-key defaults with `setQueryDefaults`. The author personally uses at least 20 seconds to deduplicate requests from components that mount at different times ([#10](https://tkdodo.eu/blog/react-query-as-a-state-manager#customize-staletime)).
- With a push channel such as WebSockets, a very high `staleTime` plus invalidation on events replaces refetching ([#7](https://tkdodo.eu/blog/using-web-sockets-with-react-query#increasing-staletime)). For forms that copy server data, `staleTime: Infinity` avoids pointless refetches ([#14](https://tkdodo.eu/blog/react-query-and-forms)).
- `staleTime: 'static'` marks data that never refetches, not even on invalidation ([#25](https://tkdodo.eu/blog/automatic-query-invalidation-after-mutations#exclude-queries-depending-on-staletime), updated November 2025). In 5.104 a query counts as static only while one of its observers uses `'static'` ([`isStatic`](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/query-core/src/query.ts#L420-L429)), so passing `'static'` to an imperative call in a loader does not stop later invalidations.
- **Against #146:** decision 3 (`gcTime: Infinity`) goes further than anything in the series, but it removes the risks the series warns about: pushed or prefetched data being collected before use ([#17](https://tkdodo.eu/blog/seeding-the-query-cache#push-approach)), and loader data being collected because nothing observes it ([#32](https://tkdodo.eu/blog/tan-stack-router-and-query#always-use-a-query)). Decision 2 (`staleTime: 0`) is the library default the series calls aggressive but valid.

### Loading states and status checks

- A query is `pending` (no data), `success` or `error`; `isFetching` is separate, so a query can be fetching while it shows data ([#4](https://tkdodo.eu/blog/status-checks-in-react-query)). A loading state belongs only to `pending`.
- Check `data` first, then `error`, then show the loading state. Checking error first replaces good cached data with an error screen when an automatic background refetch fails ([#4](https://tkdodo.eu/blog/status-checks-in-react-query#background-errors)).
- A new key is a new cache entry, so the first switch to it shows a hard loading state ([#1](https://tkdodo.eu/blog/practical-react-query#a-new-cache-entry)). To keep the previous data while a new key loads, use `placeholderData: keepPreviousData` and check `isPlaceholderData` ([#15](https://tkdodo.eu/blog/react-query-fa-qs#loading-states)).
- Stale-while-revalidate means a screen that mounts later renders cached data without a spinner ([#10](https://tkdodo.eu/blog/react-query-as-a-state-manager#stale-while-revalidate)); a component that only mounts after the data loaded triggers another request unless `staleTime` is raised.
- `fetchStatus` adds `paused` for queries waiting for a connection ([#13](https://tkdodo.eu/blog/offline-react-query#fetchstatus)); with the default `networkMode: 'online'`, a query without data that starts offline is pending and paused rather than failing. What to show is left to the app. This is relevant for the Capacitor shells on flaky mobile connections.

### Placeholder and initial data

- `initialData` is written to the cache and counts as real data, so `staleTime` applies to it; `initialDataUpdatedAt` dates it. `placeholderData` lives on one observer, is never cached, always triggers a fetch, and disappears if that fetch fails ([#9](https://tkdodo.eu/blog/placeholder-and-initial-data-in-react-query#differences)).
- To seed a detail query from a cached list, pull with `initialData` from `getQueryData` and pass the list's `dataUpdatedAt` as `initialDataUpdatedAt`, or push detail entries from the list's `queryFn` with `setQueryData` ([#17](https://tkdodo.eu/blog/seeding-the-query-cache#seeding-details-from-lists)). Both need the list item to have the detail's shape; otherwise use `placeholderData` ([#17](https://tkdodo.eu/blog/seeding-the-query-cache#push-approach)).
- `initialData` combined with a `staleTime` explains a `queryFn` that never runs ([#15](https://tkdodo.eu/blog/react-query-fa-qs#why-is-the-queryfn-not-called)).
- **For cup:** seeding the audiobook query from a Recents card would avoid the first-visit skeleton only if the history item had the audiobook's shape. `useSuspenseQuery` forces `placeholderData` to `undefined` ([`useSuspenseQuery.ts`](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/react-query/src/useSuspenseQuery.ts#L90-L100)), so the placeholder route is closed on Suspense screens.

### Suspense and `useSuspenseQuery`

- Several `useSuspenseQuery` calls in one component run as a waterfall, because each suspends before the next starts. Start the fetches earlier (router loader, `prefetchQuery`) or use `useSuspenseQueries` ([#17](https://tkdodo.eu/blog/seeding-the-query-cache#suspense-waterfalls)).
- Making a deep component's data dependency explicit has the same waterfall risk as Suspense; in v5 `useSuspenseQuery` guarantees defined `data` ([#22](https://tkdodo.eu/blog/react-query-and-react-context#suspense)).
- With TanStack Router, `useSuspenseQuery` uses the route's pending and error boundaries, so components handle only the success case; set `defaultPendingComponent` and `defaultErrorComponent` once ([#32](https://tkdodo.eu/blog/tan-stack-router-and-query#usequery-or-usesuspensequery)). A loader that awaits nothing plus `useSuspenseQuery` behaves like an awaited loader; `useQuery` then marks data the screen can show later ([#32](https://tkdodo.eu/blog/tan-stack-router-and-query#to-await-or-not-to-await-in-the-loader)).
- Library check: suspense mode raises `staleTime` and a numeric `gcTime` to at least 1,000 ms ([`ensureSuspenseTimers`](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/react-query/src/suspense.ts#L21-L47)); `gcTime: Infinity` is unaffected.

### Prefetching and router loaders

- Routers know the next page before it renders, so loaders should start fetches; but a router is not a cache, so the Query cache should hold the data ([#16](https://tkdodo.eu/blog/react-query-meets-react-router#its-not-a-cache), [#32](https://tkdodo.eu/blog/tan-stack-router-and-query#combining-query-and-router)).
- The 2022 post returns `getQueryData(key) ?? fetchQuery(...)` from the loader: cached data, even stale, renders instantly, and errors reach the route's error element; `prefetchQuery` would swallow them ([#16](https://tkdodo.eu/blog/react-query-meets-react-router#getquerydata--fetchquery)). A `fetchQuery` with a `staleTime` is the alternative, but invalidation then makes the loader wait. Version 4.18 added `ensureQueryData` for this pattern.
- The 2026 post: pass the one `QueryClient` through the router context, set `defaultPreloadStaleTime: 0` so only Query controls caching, await `ensureQueryData` in the loader, and read with `useSuspenseQuery` ([#32](https://tkdodo.eu/blog/tan-stack-router-and-query#add-the-queryclient-to-the-router-context)). Which imperative method the loader calls hardly matters, he argues, and an RFC unifies them as `queryClient.query`.
- Always read through a Query hook, not `useLoaderData`: without an observer the query gets no focus or reconnect refetches, invalidation does not refetch it, and it can be garbage collected ([#32](https://tkdodo.eu/blog/tan-stack-router-and-query#always-use-a-query)). Treat the loader as an event handler that primes the cache; pages should still work without it ([#32](https://tkdodo.eu/blog/tan-stack-router-and-query#treat-the-loader-as-an-event-handler)). In his words, a loader is "a point in time to initiate data fetching".
- With `prefetch: 'intent'`, loaders double as prefetch-on-hover ([#32](https://tkdodo.eu/blog/tan-stack-router-and-query#combining-query-and-router)). The series does not discuss touch devices; the sibling research found that `intent` fires on `touchstart`.
- Waiting for an invalidation is a lever: await it in an action to show fresh data after the redirect, or skip the await to navigate at once and refresh in the background ([#16](https://tkdodo.eu/blog/react-query-meets-react-router#await-is-the-lever)).

### Query keys, factories and `queryOptions`

- Treat the key like a dependency array: everything the `queryFn` uses belongs in the key, and filters change the key instead of calling `refetch` with parameters ([#1](https://tkdodo.eu/blog/practical-react-query#treat-the-query-key-like-a-dependency-array), [#15](https://tkdodo.eu/blog/react-query-fa-qs#how-can-i-pass-parameters-to-refetch)). Read parameters from the key through the `QueryFunctionContext` so key and fetch cannot drift apart ([#8a](https://tkdodo.eu/blog/leveraging-the-query-function-context)).
- Use array keys structured from generic to specific, one factory per feature, colocated with the feature rather than in one global keys file; prefix matching then invalidates a whole feature, all lists, or one detail ([#8](https://tkdodo.eu/blog/effective-react-query-keys#structure)). Watch type mismatches such as `'1'` versus `1` from URL params ([#15](https://tkdodo.eu/blog/react-query-fa-qs#1-query-keys-are-not-matching)).
- Since v5, `queryOptions` factories replace separate key factories and custom hooks: the author now calls separating key and function a mistake ([#24](https://tkdodo.eu/blog/the-query-options-api#query-factories)). Key-only entries such as `all()` and `lists()` sit next to full option entries. Factories should not take per-screen options; spread `select`, `staleTime` or `throwOnError` at the call site ([#31](https://tkdodo.eu/blog/creating-query-abstractions#composing-queryoptions)).
- **Against #146:** decision 5 (keys grouped by owner, factories in `src/data-fetching/` as the only place keys are built) follows #8 and #24. Cup's per-owner modules in one folder are close to the colocation advice, though not inside feature folders.

### Mutations, invalidation and `setQueryData`

- Prefer invalidation; update the cache directly with `setQueryData` when the mutation returns the full entity, and keep optimistic updates for small, rarely failing changes ([#12](https://tkdodo.eu/blog/mastering-mutations-in-react-query#tying-mutations-to-queries)). Direct edits duplicate server logic, for example sort order ([#12](https://tkdodo.eu/blog/mastering-mutations-in-react-query#direct-updates)).
- Invalidation refetches active queries and only marks inactive ones stale, so a broad invalidation, even of everything from a global `MutationCache` `onSuccess`, costs little ([#25](https://tkdodo.eu/blog/automatic-query-invalidation-after-mutations#but-isnt-that-excessive)). Narrow it with `mutationKey` or `meta` tags if needed ([#25](https://tkdodo.eu/blog/automatic-query-invalidation-after-mutations#tying-invalidation-to-specific-queries)).
- Return the invalidation promise from the callback to keep the mutation pending until the refetch is done; await only the queries that matter, with `cancelRefetch: false` to join an in-flight refetch ([#12](https://tkdodo.eu/blog/mastering-mutations-in-react-query#awaited-promises), [#25](https://tkdodo.eu/blog/automatic-query-invalidation-after-mutations#to-await-or-not-to-await)).
- Put cache logic in `useMutation` callbacks; callbacks passed to `mutate` do not run if the component unmounts first, so use them only for UI such as redirects and toasts ([#12](https://tkdodo.eu/blog/mastering-mutations-in-react-query#some-callbacks-might-not-fire)).
- Before writing to the cache, call `cancelQueries` for the affected keys, or an in-flight refetch overwrites the edit; with concurrent mutations, invalidate only when the last related one settles, using `isMutating` with a shared `mutationKey` ([#29](https://tkdodo.eu/blog/concurrent-optimistic-updates-in-react-query#query-cancellation)).
- A key-factory hierarchy allows a combined approach: update the active entry with `setQueryData`, invalidate the others with `refetchType: 'none'` ([#8](https://tkdodo.eu/blog/effective-react-query-keys#use-query-key-factories)). Updating many entries with `setQueriesData` handles neither additions nor deletions well, which is why the author falls back to invalidation ([#7](https://tkdodo.eu/blog/using-web-sockets-with-react-query#partial-data-updates)).
- An infinite query is one cache entry; a refetch rebuilds all its pages in order from the first ([#26](https://tkdodo.eu/blog/how-infinite-queries-work)), and `maxPages` limits how many are kept ([#27](https://tkdodo.eu/blog/react-query-api-design-lessons-learned)).
- **Against #146:** decision 4 (invalidate broadly, edit narrowly, always invalidate after an edit) is the series' position. For decision 6, removing a deleted conversion from the cached history pages, #29 implies cancelling any in-flight history fetch first: the history polls while a conversion runs, and a poll that started before the delete would bring the card back.

### Polling

- The series says little about polling. Turning `refetchInterval` off through `enabled` pauses it, for example while a modal is open ([#1](https://tkdodo.eu/blog/practical-react-query#the-enabled-option-is-very-powerful)); almost every option accepts a function of the query, so behaviour can depend on query state ([#27](https://tkdodo.eu/blog/react-query-api-design-lessons-learned)); a push channel plus invalidation is the alternative ([#7](https://tkdodo.eu/blog/using-web-sockets-with-react-query)). Interval refetching is one reason to keep React Query even with server-side data fetching ([#20](https://tkdodo.eu/blog/you-might-not-need-react-query)).
- Library check: the interval belongs to an observer, so a query nobody renders does not poll, and each tick fetches only while the document is visible unless `refetchIntervalInBackground` is set ([`#updateRefetchInterval`](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/query-core/src/queryObserver.ts#L517-L536)). Cup's audiobook query sets `refetchIntervalInBackground: true` (`apps/web-app/src/data-fetching/reader.ts`).
- Nothing in the series covers screens hidden in `<Activity>`; that stays with the map's "Polling off screen" item.

### Error handling when cached data exists

- `fetch` does not reject on HTTP errors; the `queryFn` must throw, and catching an error for logging without rethrowing turns it into success ([#11](https://tkdodo.eu/blog/react-query-error-handling#prerequisites), [#15](https://tkdodo.eu/blog/react-query-fa-qs#why-do-i-not-get-errors)).
- Combine three tools: the `error` field for local display, error boundaries through `throwOnError` (a function lets 4xx stay local and send 5xx to the boundary), and toasts from the global `QueryCache` `onError`, which runs once per failed fetch ([#11](https://tkdodo.eu/blog/react-query-error-handling#error-boundaries)). The author's own mix: a toast for failed background refetches (`query.state.data !== undefined`), local handling or boundaries for the rest ([#11](https://tkdodo.eu/blog/react-query-error-handling#putting-it-all-together)).
- Library check: `useSuspenseQuery` always passes its own `throwOnError`, which throws only when the query has no data ([`defaultThrowOnError`](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/react-query/src/suspense.ts#L11-L19), [`useSuspenseQuery`](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/react-query/src/useSuspenseQuery.ts#L90-L100)), and an error is thrown only once fetching has stopped ([`getHasError`](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/react-query/src/errorBoundaryUtils.ts#L51-L78)). A failed refetch with cached data therefore keeps rendering the data, with `error` set on the result.
- **Against #146:** cup's `QueryCache` `onError` already implements the #11 pattern (toast only when the query has data, opt-out through `meta`), so the "other failures keep the content and toast" half of decision 10 matches the series. The other half, showing the error screen when a revisit refetch gets _not found_ or _access denied_, is stricter than the series, which prefers keeping stale data. With `useSuspenseQuery` it cannot come from `throwOnError`; one way is for the screen to read `error` from the result and throw it during render for those two cases, so the route's error component shows. That is my inference, not tested.

### Testing

- Mock the network with Mock Service Worker, create a new `QueryClient` per test inside the wrapper, turn retries off on the test client (and set per-query options through `setQueryDefaults` so tests can override them), and await results with `waitFor` ([#5](https://tkdodo.eu/blog/testing-react-query)). Provide the client through context and read it with `useQueryClient`, so tests can inject their own defaults ([#15](https://tkdodo.eu/blog/react-query-fa-qs#2-it-decouples-your-app-from-the-client)).
- The series never tests that a loading state is absent. Cup already turns retries off in its production defaults.

## Outside the series

[Reliable Query Prefetching with TanStack Router](https://tkdodo.eu/blog/reliable-query-prefetching-with-tanstack-router) (August 2026, part 4 of the author's TanStack Router series, not one of the 33) was skimmed because it addresses loader and component drifting apart: build the route's `queryOptions` once in the route's `context` function (with `loaderDeps` for the search params that identify the data), and use the same object in the loader and in `useSuspenseQuery`.
