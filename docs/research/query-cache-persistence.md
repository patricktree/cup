# Persisting the TanStack Query cache across app restarts

> Historical research, incorporated 2026-10-30. Cited by [ADR 0016](../adr/0016-keep-the-query-cache-for-the-page-lifetime-and-load-screens-in-route-loaders.md), which rejects persistence ([#154](https://github.com/patricktree/cup/issues/154)); the cache lives for the [page lifetime](../architecture/web-app.md#query-cache) only and nothing below is built. Unlike the plan this page assumed, routes settle auth through `settleAccountSession`, and the detail view has no `beforeLoad`, since its request waits for any session itself. Repository observations below describe `664dba9`.

[Original investigation](https://github.com/patricktree/cup/blob/120d8676b38930119f36855ca23eb952be903b58/docs/research/query-cache-persistence.md).

Research date: 2026-10-29, for [issue #153](https://github.com/patricktree/cup/issues/153) of the [map: navigate the web app without loading flashes](https://github.com/patricktree/cup/issues/143). Library behaviour was read from the installed `@tanstack/react-query` / `@tanstack/query-core` 5.104.1 and, for the persister packages that Cup does not install, from TanStack/query commit [`29859ae`](https://github.com/TanStack/query/tree/29859ae60c8dca0a5cdbf8abccc775b655cf43e2), whose `query-persist-client-core` is also 5.104.1 and which the [sibling research](router-query-loading-interplay.md) matched against `node_modules`. Repository observations are from `main` at [`664dba9`](https://github.com/patricktree/cup/tree/664dba938eaa7605deabdd4446ff420a951059a2). Nothing was run in a browser or a shell. This page gathers facts; [Whether to persist the query cache across app restarts](https://github.com/patricktree/cup/issues/154) decides.

## Question

What would it take to persist the web app's TanStack Query cache across page reloads and app restarts in the browser and the Capacitor shells, and what would it buy and cost against the map's rules? In particular: would a restored cache plus loaders that read with `queryClient.query({ ...options, staleTime: 'static' })` let a cold start render cached content without a skeleton, and what auth and sign-out handling would that need?

## Answer

- **Yes, with one change to start-up order, and only once auth has settled.** If the restore finishes before the router's first load, a loader's `queryClient.query({ ..., staleTime: 'static' })` returns restored data without a request, because `'static'` data is never stale ([`isStaleByTime`](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/query-core/src/query.ts#L473-L488)). The screen's `useSuspenseQuery` then finds data, does not suspend, and refetches in the background because the restored `dataUpdatedAt` is older than the 1 s suspense floor. That is rule 1's behaviour on a cold start.
- **`PersistQueryClientProvider` does not give that order.** It restores in a `useEffect` after the first render ([provider](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/react-query-persist-client/src/PersistQueryClientProvider.tsx#L25-L48)), and its `isRestoring` gate only reaches Query hooks, not router loaders. Cup would await `persistQueryClientRestore` itself, before `router.load()` / the first render or in the root `beforeLoad`, and then call `persistQueryClientSubscribe`.
- **Auth still costs a network round trip on every cold start.** Every data route awaits `ensureAuthInitialized()` in `beforeLoad`, which first fetches `getAuthConfig` and then calls Supabase `getSession`, which refreshes an expired access token over the network ([Supabase docs](https://supabase.com/docs/reference/javascript/auth-getsession)); the local `supabase/config.toml` sets `jwt_expiry = 300`. A persisted cache removes the data request, not the auth requests, so a cold start still waits for the network and fails offline. Whether the skeleton shows depends on whether auth finishes within `pendingMs` (500 ms).
- **Restoring before auth settles would show one account's data to another, or to nobody.** The audiobook and grant keys carry no subject, and `queryClient.query` with `'static'` serves cached data without asking the server. The session machine deliberately keeps cached queries during the initial session restore. So the persisted cache needs an owner check: restore only after auth settles and only if the persisted owner matches the current subject (for example a `buster` of build ID plus subject), and delete the persisted copy on sign-out and account switch.
- **Mechanism of choice, if any:** `persistQueryClient` with `createAsyncStoragePersister` (the sync persister is deprecated in 5.104) over IndexedDB or Capacitor Preferences, with `shouldDehydrateQuery` limiting what is stored. The experimental per-query persister fits Cup worse: it does not persist `setQueryData` edits (decisions 6 and 7 of the cache lifetime policy rely on them) and `queryClient.clear()` leaves its stored entries in place.
- **Storage:** `localStorage` is about 5 MiB per origin and one key holds the whole dehydrated client, which a few narration documents can fill. IndexedDB has a large quota but Capacitor calls web storage on iOS transient. Capacitor recommends Preferences (UserDefaults / SharedPreferences) for small data and SQLite for large data. Safari's 7-day cap does not threaten a cache the user just used, because each use resets it.
- **Rule 3 already allows a skeleton on a cold start**, so persistence goes beyond the map's destination. It would buy a cold start that shows the last-seen content instead of a skeleton while online, at the cost of the start-up ordering, owner checks, a sign-out purge, a build-ID buster, a storage choice per platform and personal data at rest.

## Findings

### Mechanism in 5.104

**Whole-client persistence.** `persistQueryClientRestore` reads one `PersistedClient` (`{ timestamp, buster, clientState }`), discards it and calls `removeClient()` when it is older than `maxAge` (default 24 hours), has a different `buster` (default `''`), has no timestamp, or throws, and otherwise calls `hydrate` ([persist.ts](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/query-persist-client-core/src/persist.ts#L71-L106)). `persistQueryClientSubscribe` saves a fresh `dehydrate` on every `added`, `removed` or `updated` event of the query and mutation caches ([persist.ts](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/query-persist-client-core/src/persist.ts#L132-L155)), so `setQueryData`, `removeQueries` and `clear()` all reach storage. `persistQueryClient` restores and subscribes afterwards, returning `[unsubscribe, restorePromise]`.

**Persisters.** `createAsyncStoragePersister` takes any storage with `getItem` / `setItem` / `removeItem` (sync storage such as `localStorage` also fits), serializes with `JSON.stringify` by default, stores everything under one key (`REACT_QUERY_OFFLINE_CACHE`), throttles writes to one per `throttleTime` (1 s), and accepts a `retry` callback for failed writes such as a full quota ([async persister](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/query-async-storage-persister/src/index.ts#L42-L102)). `createSyncStoragePersister` is deprecated in favour of the async one ([sync persister](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/query-sync-storage-persister/src/index.ts#L42)). The throttle saves the latest state at the end of the interval, so a change made less than a second before the process dies may not reach storage. The docs show a custom IndexedDB persister over `idb-keyval` that stores the object without string serialization ([docs](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/docs/framework/react/plugins/persistQueryClient.md#building-a-persister)).

**What is stored.** `dehydrate` keeps only `success` queries by default (`defaultShouldDehydrateQuery`), unless `shouldDehydrateQuery` says otherwise; `serializeData` / `deserializeData` transform the data ([hydration.ts](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/query-core/src/hydration.ts#L186-L188)). `hydrate` keeps the stored `dataUpdatedAt`, sets `fetchStatus: 'idle'`, builds new queries with the client's defaults (so Cup's `gcTime: Infinity` applies), and never overwrites a query whose in-memory data is newer ([hydration.ts](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/query-core/src/hydration.ts#L311-L370)). The docs ask for a `gcTime` at least as long as `maxAge`, and note that `Infinity` disables collection ([docs](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/docs/framework/react/plugins/persistQueryClient.md#how-it-works)).

**Restore timing and `isRestoring`.** The docs warn that restoring is asynchronous and that rendering during it races with queries that mount and fetch ([docs](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/docs/framework/react/plugins/persistQueryClient.md#usage-with-react)). `PersistQueryClientProvider` starts with `isRestoring: true`, restores in an effect, and subscribes only afterwards. While it is restoring, `useBaseQuery` does not subscribe its observer and reports `fetchStatus: 'idle'` ([useBaseQuery](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/react-query/src/useBaseQuery.ts#L51-L94)). Nothing in the router or in `queryClient.query` reads that flag, so a loader that runs during the restore fetches from the network, and the restore then does not overwrite the newer data. In a client-only app, the robust order is to await the restore before the router loads.

**Per-query persister.** `experimental_createQueryPersister` wraps each `queryFn`: it restores a query from storage lazily, only when the query has no data and its `queryFn` runs, stores each query under `prefix-queryHash`, and writes after each successful `queryFn` ([createPersister.ts](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/query-persist-client-core/src/createPersister.ts#L204-L246)). A query with a persister defaults to `networkMode: 'offlineFirst'` (installed `queryClient.ts`, line 1047). The docs say `setQueryData` is not persisted and that `queryClient.removeQueries` leaves stored data in place, so a separate `removeQueries` on the persister is needed ([docs](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/docs/framework/react/plugins/createPersister.md)). For Cup this would lose the direct edits of decisions 6 (deleted card) and 7 (playback position) of the [cache lifetime policy](https://github.com/patricktree/cup/issues/146) across a restart unless each edit also calls `persistQueryByKey`, and `queryClient.clear()` on sign-out would leave every stored query on disk.

### Storage per platform

| Storage               | Size                                                                                                                  | Eviction                                                                                                                    | API                                                          | Source                                                                                                                                                                                             |
| --------------------- | --------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `localStorage`        | 5 MiB per origin, `QuotaExceededError` beyond                                                                         | Best-effort; Capacitor calls it transient on mobile                                                                         | Sync, strings                                                | [MDN quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [Capacitor storage guide](https://capacitorjs.com/docs/guides/storage)            |
| IndexedDB             | Chromium: up to 60% of disk per origin; WebKit: up to 60% for browser apps, 15% for other apps that embed web content | Best-effort and LRU under pressure unless `navigator.storage.persist()` is granted; Capacitor says it can be evicted on iOS | Async, structured clone                                      | [MDN quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), [WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/) |
| Capacitor Preferences | Not stated; "not meant to be used as a local database"                                                                | Native, not evicted; removed on uninstall                                                                                   | Async, strings only; falls back to `localStorage` on the web | [Preferences API](https://capacitorjs.com/docs/apis/preferences)                                                                                                                                   |
| SQLite plugin         | Large                                                                                                                 | Native                                                                                                                      | Async                                                        | [Capacitor storage guide](https://capacitorjs.com/docs/guides/storage)                                                                                                                             |

- **Safari's 7-day cap.** With tracking prevention on, Safari deletes an origin's script-writable storage (IndexedDB, `localStorage`, service worker caches and more) after seven days of Safari use without user interaction on the site; home screen web apps count their own days of use ([WebKit, 2020](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)). ITP is on by default in all `WKWebView` apps ([WebKit, app-bound domains](https://webkit.org/blog/10882/app-bound-domains/)); no WebKit post says how the 7-day count works there. Either way, a listener who opens the app interacts with its origin and resets the counter, so the cap can only drop a cache nobody has used for a week, which `maxAge` (default 24 hours) would discard anyway.
- **Persistent mode.** WebKit grants `navigator.storage.persist()` by heuristics such as being a home screen web app ([WebKit storage policy](https://webkit.org/blog/14403/updates-to-storage-policy/)); Chromium decides from interaction history without a prompt ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)).
- **Android WebView.** The persister docs note that `window.localStorage` can be `null` in an Android WebView depending on its configuration ([async persister](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/query-async-storage-persister/src/index.ts#L18-L22)). Cup's Android shell already uses `localStorage` for the trial grant and trial playback positions (`trial-browser-state.ts`, `data-fetching/reader.ts`), so it is available there.
- **Cup's shells** bundle the web build (`webDir` in `apps/mobile-app/capacitor.config.ts`), so a store update replaces the code while storage persists. Android keeps the Supabase session in `@aparajita/capacitor-secure-storage`, the web in `localStorage` ([authentication](../architecture/authentication.md)); iOS account support is deferred.
- **Size in Cup.** The audiobook response carries the whole narration document (`narrationDocument.html` plus synchronization units, `libs/listener-api.routes/src/contracts.ts`), and with `gcTime: Infinity` every audiobook opened in a session stays in the cache. Persisted as one JSON string, that can approach the `localStorage` limit after a few long articles. `shouldDehydrateQuery` can leave audiobooks out or keep only some, or IndexedDB can hold the whole cache. A failed write is silent unless `retry` handles it.

### Interplay with the decided setup

- **`gcTime: Infinity`** ([cache lifetime policy](https://github.com/patricktree/cup/issues/146), decision 3) already meets the docs' requirement of `gcTime` ≥ `maxAge`. With persistence, the cache would outlive the page, so "page lifetime" in that decision would become "until `maxAge`, sign-out or a new build".
- **`staleTime: 0`** (decision 2) means every restored query refetches when its screen mounts, which is the background refresh rule 1 wants. Suspense mode raises `staleTime` to at least 1 s ([suspense.ts](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/react-query/src/suspense.ts#L21-L46)), but the restored `dataUpdatedAt` is older than that, so the mount refetches.
- **Loaders with `staleTime: 'static'`** ([loaders ticket](https://github.com/patricktree/cup/issues/147), decision 2): `queryClient.query` fetches only when `isStaleByTime(staleTime)` is true, and with `'static'` that is only when there is no data (installed `queryClient.ts`, lines 563–602; [`isStaleByTime`](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/query-core/src/query.ts#L473-L488)). A restored query therefore returns at once, so the loader resolves immediately and the router never reaches `pendingMs`. With the per-query persister, the loader instead runs the wrapped `queryFn`, which reads storage asynchronously and makes no network request.
- **`useSuspenseQuery`** throws only without data ([suspense.ts](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/packages/react-query/src/suspense.ts#L11-L19)), so restored data renders and a failing background refetch shows the existing toast.
- **Auth in `beforeLoad`** ([loaders ticket](https://github.com/patricktree/cup/issues/147), decision 4) runs before the loader. `ensureAuthInitialized()` awaits `loadConnection`, which fetches `getAuthConfig` before creating the Supabase client, and then `readSession`, which calls `getSession` (`apps/web-app/src/auth/account-session.ts`, `account-session-machine.ts`). Both need the network on a cold start, the second whenever the stored access token has expired. So **a restored cache does not make the cold start independent of the network**; it saves the data request that would follow auth. The [first-visit prototype](https://github.com/patricktree/cup/issues/148) decided a cold start stays blank until auth settles and then shows the skeleton; with a restored cache, the screen would appear filled right after auth instead.
- **Track and cover URLs.** A signed media URL stays valid for at least 24 hours after it is handed out ([authentication](../architecture/authentication.md#signed-media-url)). Hydration keeps `dataUpdatedAt`, so the player's renewal by `dataUpdatedAt` (decision 9 of the cache lifetime policy) still renews a restored track URL after 12 hours. Restored cover URLs in the history are valid as long as `maxAge` is at most 24 hours; a longer `maxAge` could show broken covers until the background refetch replaces them.
- **Error handling for revisits** (decision 10): a restored audiobook that was deleted or a grant that was revoked meanwhile would render, then the mount refetch would get _not found_ or _access denied_ and show the error screen. Content would flash before the error.

### Risks

- **Another account's data, or a signed-out listener's.** `queryClient.clear()` runs on sign-out and on a subject change while connected, which `persistQueryClientSubscribe` would write through within the 1 s throttle. But the initial session restore keeps cached queries on purpose (`account-session-machine.ts`, `restoringSession`), and a session that expired or was revoked while the app was closed restores as signed out without clearing. The audiobook key (`["audiobook", conversionId]`) and the grant key carry no subject, and a `'static'` loader read asks no server, so the detail view would show a previous account's audiobook to whoever opens the app next. Options: restore only after auth settles, with a `buster` that includes the subject (a mismatch makes `persistQueryClientRestore` delete the stored copy); call `persister.removeClient()` directly on sign-out and account switch rather than relying on the throttled save; or exclude audiobook and grant queries via `shouldDehydrateQuery`.
- **Personal data at rest.** Narration text, titles, history and account details would sit unencrypted in web storage or Preferences. On the web this is the same origin storage that already holds the Supabase session; on Android the session is in secure storage but the cache would not be. Sign-out purges it only if the purge runs.
- **Signed URLs at rest.** A signed media URL is a bearer credential for its lifetime and local sign-out does not invalidate it ([authentication](../architecture/authentication.md#signed-media-url)), so a persisted cache stores working media links until they expire.
- **Schema drift between app versions.** A restored cache skips the `zod` parse that `queryFn` applies (`audiobookSchema.parse` in `data-fetching/reader.ts`), so data stored by an older build reaches newer components unchecked. The documented fix is a `buster` per build ([docs](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/docs/framework/react/plugins/persistQueryClient.md#cache-busting)), which empties the cache after every deploy; on the web, Cup deploys on every push to `main`.
- **Serialization.** The default is `JSON.stringify` / `JSON.parse`. Cup's API responses are parsed from JSON by `zod` schemas whose fields are strings, numbers, booleans and arrays (`contracts.ts`), so they round-trip. Failed queries, whose errors are `RpcError` instances, are not dehydrated by default.
- **Write failures** (quota exceeded) and **lost last writes** (process killed within the throttle interval) are silent unless `retry` and an explicit `removeClient` cover them.

### Practice

- The TanStack docs present persistence as a plugin for keeping the cache across reloads and for offline use, require a `gcTime` ≥ `maxAge`, and recommend a `buster` for breaking changes ([docs](https://github.com/TanStack/query/blob/29859ae60c8dca0a5cdbf8abccc775b655cf43e2/docs/framework/react/plugins/persistQueryClient.md)). They give no rule for when it is worth it.
- TkDodo's [offline post](https://tkdodo.eu/blog/offline-react-query) covers `networkMode` and the in-memory cache, not persistence; no post in the Practical React Query series (read for [#151](https://github.com/patricktree/cup/issues/151)) recommends persisting the cache. A search found no TkDodo post on when persistence pays off.
- **TanStack Router.** No documented integration exists. The one router issue found ([TanStack/router#1983](https://github.com/TanStack/router/issues/1983)) shows a persisted cache plus `PersistQueryClientProvider` rendering differently once a route had a loader; a maintainer suggested moving data loading into loaders so data is present on the first render. This supports awaiting the restore before the router loads.
- **React 19.** No React 19-specific pitfall was found. An open issue about `PersistQueryClientProvider` with Suspense ([TanStack/query#6472](https://github.com/TanStack/query/issues/6472)) concerns server rendering, which Cup does not use. During a provider restore, a suspense hook whose query has no data still suspends and fetches, because `isRestoring` only idles the observer; awaiting the restore before rendering avoids this.

## What a persisted setup would involve

This lists the pieces the decision would weigh. It is not a recommendation.

1. Add `@tanstack/react-query-persist-client` and `@tanstack/query-async-storage-persister` at 5.104.1, and pick a storage adapter per platform (IndexedDB on the web, Preferences or a SQLite plugin in the shells, or `localStorage` everywhere with a narrow `shouldDehydrateQuery`).
2. At start-up, settle auth first, then `await persistQueryClientRestore({ queryClient, persister, maxAge, buster })` with a `buster` made of the build ID and the subject (or a signed-out marker), then `persistQueryClientSubscribe`, all before the router's first load (for example inside the root route's `beforeLoad`, after `ensureAuthInitialized()`).
3. Call `persister.removeClient()` in the session machine's `clearQueries` action, and also when the initial restore finds no session or a different one.
4. Choose `maxAge` ≤ 24 hours so restored signed media URLs stay valid.
5. Test: a cold start with a stored cache renders the cached screen without its `pendingComponent`; a cold start after sign-out, account switch or a new build renders nothing from the old cache.
