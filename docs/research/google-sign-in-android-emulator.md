# Real native Google sign-in on an Android emulator

> Historical research, incorporated 2026-11-10 by [ADR 0018](../adr/0018-test-the-mobile-apps-with-appium-through-webdriverio-on-host-owned-emulators-and-simulators.md), whose rejection of a real Google sign-in cites its per-machine cost. One of two investigations of [issue #187](https://github.com/patricktree/cup/issues/187); the other is [Testing a real native Google sign-in on an Android emulator](native-google-sign-in-testing.md). Cup did not build a real sign-in: [patricktree/cup#183](https://github.com/patricktree/cup/issues/183) chose a debug-only fake of the Google sign-in plugin plus one test that opens and cancels Google's add-account screen, and the real sign-in is future work in [CUP-59](https://linear.app/cup-audio/issue/CUP-59/test-a-real-native-google-sign-in-on-the-android-emulator). External claims have not been reverified.

[Original investigation](https://github.com/patricktree/cup/blob/abb139d4897bc0c7bc41f2da8f703d869d414556/docs/research/google-sign-in-android-emulator.md).

Research date: 2026-11-06, for [issue #187](https://github.com/patricktree/cup/issues/187) of the [automated mobile QA map](https://github.com/patricktree/cup/issues/179). Repository observations are from `main` at `626776ac`, with `@capawesome/capacitor-google-sign-in` `0.1.4` (androidx Credentials `1.5.0`, `googleid` `1.1.1`, `play-services-auth` `21.5.0` by the plugin's defaults). Web sources were read on the research date. One probe ran on the developer's Mac the same day: the current debug build, installed on a `-read-only` boot of the existing `ContentPushPixel36` AVD (`android-36;google_apis_playstore;arm64-v8a`, Google Play services `26.15.33`, no Google account on the device). No Google account was signed in or created, and no Google Cloud setting was read or changed. Points marked _unverified_ need a prototype with a real test account.

## Question

What does it take for an automated test on an Android emulator to complete a **real** native Google sign-in in Cup's debug build: open the Credential Manager "Sign in with Google" flow (`GetSignInWithGoogleOption`), choose a Google account and receive a real ID token? What does each approach cost per developer machine, and is that cost really a new Google Cloud setup on every machine? The ticket also asks about Google's checks and error messages, a committed debug keystore, Google Play images and Quick Boot snapshots with a signed-in test account, Google's anti-automation measures, whether UI Automator or Appium can drive the sheet, how the token becomes a Cup session, and Google's own testing guidance.

## Answer

Real native sign-in needs a per-machine Google Cloud step only because every machine signs debug builds with its own auto-generated `~/.android/debug.keystore`, and Google binds an Android OAuth client to one package name and signing certificate. Committing one debug keystore and pointing `signingConfigs.debug` at it removes that step: one Android client, registered once, covers every checkout. What stays per machine is a Google test account signed in on the emulator, which a person has to do by hand, and which Google's sign-in protections can interrupt at any time. Opening and dismissing Google's flow needs none of this: on the probe it opened with no account on the device, before Google checks the signing certificate.

| Approach                                                                        | One-time cost                                                                                                              | Per-machine cost                                                                                                                      | Per-run needs                                        | Risk                                                                                                         |
| ------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Real sign-in, each machine's own debug keystore                                 | A Google Cloud project with a web client and the OAuth consent screen; a dedicated Google test account                     | An Android OAuth client for this machine's SHA-1 (Cloud console access); sign the test account into a suite-owned AVD and snapshot it | Internet; Google's servers; the test account's grant | Account challenges and lockouts; Cloud access for every developer; unused clients are deleted after 6 months |
| Real sign-in, a committed debug keystore                                        | As above, plus one Android client for the committed keystore's SHA-1, and a committed keystore with `signingConfigs.debug` | Sign the test account into a suite-owned AVD once, by hand, with its password and second factor, and snapshot it                      | Same as above                                        | Same account risks; anyone can sign an `audio.cup.app` build that Google accepts for this client             |
| Open and dismiss Google's flow, fake the rest (no Google account on the device) | None                                                                                                                       | None                                                                                                                                  | Internet for Google's add-account page               | Google's UI and its process can change; the WebView reloaded after cancellation once in the probe            |
| Stub the plugin, no Google UI                                                   | None                                                                                                                       | None                                                                                                                                  | None                                                 | Leaves Google's flow and Credential Manager untested                                                         |

A committed keystore removes the Cloud console from every machine but not the person: each machine still needs a human to sign the test account into the emulator once, and to sign in again whenever Google ends the device session or challenges the account. The recommendation at the end weighs this against the open-and-dismiss fallback.

## What Google checks before it returns an ID token

Cup's Android adapter calls `GoogleSignIn.initialize({ clientId })` with the **web** client ID from the Worker's auth configuration, hashes a random nonce with SHA-256, calls `GoogleSignIn.signIn({ nonce: hashedNonce })`, and exchanges the returned ID token and the raw nonce with Supabase through `signInWithIdToken` ([`account-auth.android.ts`](../../apps/web-app/src/platform/account-auth.android.ts)). A "fresh" sign-in first calls `signOut()`, which clears Credential Manager state. Sources: [Android adapter](../../apps/web-app/src/platform/account-auth.android.ts), [session facade](../../apps/web-app/src/auth/account-session.ts).

The plugin builds a `GetSignInWithGoogleOption` with that web client ID as its server client ID and sets only the nonce; it sets no hosted-domain filter, and `filterByAuthorizedAccounts` and auto-select do not exist on this option (they belong to `GetGoogleIdOption`). It requests the credential with `CredentialManager.getCredentialAsync` and maps errors: `GetCredentialCancellationException` to `SIGN_IN_CANCELED` (keeping Google's message), `NoCredentialException` to `NO_CREDENTIAL_AVAILABLE`, `GetCredentialProviderConfigurationException` to `PROVIDER_CONFIGURATION_ERROR`, and anything else to an exception carrying the Credential Manager error type. Source: the plugin's [`GoogleSignIn.java`][plugin-java] and [`CustomExceptions.java`][plugin-exceptions].

Google relates three things before it issues a token for the web client ID:

- **A web OAuth client**, whose ID becomes the token's `aud` and which the app passes as server client ID ([implementation guide][siwg-impl]).
- **An Android OAuth client in the same project**, registered with the app's package name and the SHA-1 of the certificate that signs the installed APK. The plugin's README states that the Android client ID "is never passed to the plugin" but "must still exist and match the app, otherwise the sign-in flow fails" ([plugin README][plugin-readme]). Google's own account of this: "Android OAuth client IDs are linked to specific certificate/package pairs" and "You only need one ID for each certificate" ([Google Fit: Get an OAuth 2.0 client ID][fit-client]); Sign-in "require[s] you to provide the SHA-1" ([Authenticating your client][client-auth]).
- **The Google Auth Platform configuration** (consent screen, brand) of the project ([Sign in with Google overview][siwg]).

What fails when the SHA-1 is not registered: the plugin's README says that "the account picker opens but the flow fails as soon as an account is picked", logging `Auth.Api.Credentials: … [8] Unknown error [status=UNREGISTERED_ON_API_CONSOLE]` and `[16] Account reauth failed`, and that "Google Play services reports this as a cancellation", so the call rejects with `SIGN_IN_CANCELED` and the message `Account reauth failed` ([plugin README][plugin-readme], [source comment][plugin-java]). Google's troubleshooting guide confirms the pattern without naming the SHA-1: a `GetCredentialCancellationException` "can also signal that the request was not authorized due to technical constraints", and a high volume of cancellations "may actually indicate a misconfiguration" ([troubleshooting][troubleshooting]). The messages `[28444] Developer console is not set up correctly` (from Credential Manager) and `ApiException: 10` / `DEVELOPER_ERROR` (from the legacy Google Sign-In and One Tap APIs) appear in community reports for the same mismatch of package, SHA-1 or web client ID ([Capgo troubleshooting][capgo-troubleshooting]); Google's documentation does not list them, so which of these Cup's stack would print is _unverified_.

Whether the flow opens at all:

- **No Google account on the device.** Google's guide says the bottom sheet (`GetGoogleIdOption`) does not appear without accounts and returns `NoCredentialException`, while "the button allows users to add a new account to the device" ([Sign in with Google overview][siwg], [troubleshooting][troubleshooting]). Cup uses the button option. The probe confirmed it: tapping "Continue with Google" in Cup's sign-in dialog started `CredentialChooserActivity`, then `GoogleSignInActivity`, then Google's add-account screen `MinuteMaidActivity` ("Sign in with ease", with NEXT and SKIP), all in `com.google.android.gms`. Logcat showed the platform `CredentialManager` routing the request to Play services' `GoogleIdService`.
- **Unregistered SHA-1.** The flow opens, because Google checks the client after an account is chosen ([plugin README][plugin-readme]). The probe's machine-specific debug SHA-1 is most likely not registered on production's Android client, and the add-account screen still opened; the failure after choosing an account is _unverified_ here, since no account was signed in.
- **Cancellation.** Pressing Back on the add-account screen logged `Auth.Api.Credentials: … [16] Cancelled by user.` and returned to Cup, which the plugin maps to `SIGN_IN_CANCELED`. Cup's WebView restarted right after (`Capacitor: Starting BridgeActivity` 0.7 s later); whether Android had killed Cup's process behind Google's activity on the 2 GB emulator, or something else recreated the activity, is _unverified_, but a test that dismisses the flow has to expect it.

## Does a committed debug keystore remove the per-machine step?

Android Studio "automatically creates the debug keystore and certificate in `$HOME/.android/debug.keystore`" the first time it builds ([Sign your debug build][app-signing]). Cup's [`build.gradle`](../../apps/mobile-app/android/app/build.gradle) declares no `signingConfigs`, so every machine signs debug builds with its own generated key; on this Mac `keytool -list -v` shows `CN=Android Debug`, created 10 Feb 2026 and valid 30 years, with a SHA-1 that belongs to this machine alone (not reproduced here). With one Android client per package and certificate ([Google Fit][fit-client]), each machine therefore needs its own Android client, which is the per-machine Google Cloud step the ticket suspects.

Several SHA-1s on one client: no Google page states that one Android client can hold several fingerprints. Google's console instructions take one package name and one SHA-1 per client ([Manage OAuth clients][manage-clients]), Google's Fit guide says one client per certificate, and the plugin says "Add an OAuth client for every fingerprint you want to support" ([plugin README][plugin-readme]). A project may hold many Android clients; Google names no limit on them, only two secrets per client ([Manage OAuth clients][manage-clients]). Each package and SHA-1 pair "must be unique across all Firebase and Google Cloud projects" ([Firebase help][firebase-unique]). The console also deletes "OAuth 2.0 clients that have been inactive for six months" ([Manage OAuth clients][manage-clients]), so a client only used by an occasional test suite can disappear.

A committed keystore turns this into a one-time step. A `signingConfigs.debug` block pointing `storeFile` at a keystore in the repository, with the well-known passwords, makes every checkout sign debug builds with the same certificate; the Android Gradle plugin supports any keystore in a signing configuration ([Configure the build process to sign your app][app-signing]). One Android client for `audio.cup.app` and that SHA-1 then serves every machine. This was not built here; it is _unverified_ only in the sense that no sign-in completed.

Test-only OAuth clients and the "Testing" status: Google has no separate "test" client type; the closest equivalent is a separate Google Cloud project for development and tests, with its own web client and the Android client for the committed keystore. The Supabase guide recommends separate fingerprints for local testing and production, listing all web and Android client IDs in the Google provider's comma-separated client ID list ([Supabase: Login with Google][supabase-google]). A project in "Testing" publishing status is limited to 100 test users and test-user authorizations "expire seven days from the time of consent", but there is an exception: apps that request only the name, email and profile scopes skip the test-user list, and their authorizations do not expire after 7 days ([Manage app audience][app-audience]). Cup requests no extra scopes (`initialize` gets no `scopes`), and ID tokens are not refresh tokens, so the Testing status does not limit Cup's sign-in tests.

Security of committing a debug keystore. Google says not to publish an app signed with a debug certificate and to "Only use this certificate with apps that you're testing" ([Google Fit][fit-client]); Android Studio calls the debug certificate "insecure by design" ([Sign your debug build][app-signing]). Once the keystore is public, anyone can sign an APK named `audio.cup.app` with it, and Google will issue ID tokens for the web client tied to that Android client to whoever signs in with that APK. The harm depends on where those tokens are accepted:

- If the Android client sits in **production's** project, a lookalike app on a victim's phone could obtain a genuine ID token for Cup's production web client and exchange it with production Supabase, signing the attacker into the victim's Cup account. Today a local machine's debug SHA-1 would carry the same risk only if it leaked.
- If it sits in a **separate test project** whose web client ID production Supabase does not list, the tokens are useless against production: Supabase and Google's own verification reject an `aud` that is not one of the app's client IDs ([Verify the Google ID token][verify-id-token]). The remaining risk is a lookalike app on someone's phone showing Cup's test project name on Google's consent screen, which a project without brand verification shows only as an unverified app ([Sign in with Google overview][siwg]).

The release signing key is unaffected: Play App Signing uses its own app signing key, and Google says to create a separate client for the production app ([Manage OAuth clients][manage-clients], [app signing][app-signing]). Because package and SHA-1 pairs are globally unique ([Firebase help][firebase-unique]), registering the committed SHA-1 first also prevents anyone else from claiming that pair for `audio.cup.app`.

## A Google test account on the emulator

Image choice. Images labeled Google APIs include Google Play services; Google Play images add the Play Store, offer a button to update Play services, and are signed with a release key, so they have no root ([Create and manage virtual devices][managing-avds]). This Mac has `android-36;google_apis_playstore;arm64-v8a` (the sibling research's choice), `android-36.1;google_apis_playstore;arm64-v8a` and `android-35;google_apis;arm64-v8a`. The API 36 Play image ran Play services `26.15.33` with the platform Credential Manager and Play services' `GoogleIdService` registered as a provider. Credential Manager needs Play services `230815045` or later through androidx, and Google's known multi-account bug is fixed from `24.40` ([androidx Credentials release notes][credentials-releases], [troubleshooting][troubleshooting]), so any current Play or Google APIs image is new enough. A Google APIs image cannot update Play services from the Store, so its version only moves with a new image.

Signing in once and snapshotting. A person adds the test account through Settings on a suite-owned AVD, opens Cup and completes one sign-in, so Google records the grant, then saves the Quick Boot snapshot; later runs start it with `-read-only`, which discards every change ([sibling research on emulators](https://github.com/patricktree/cup/issues/181)). The add-account flow is Google's web sign-in page inside Play services; Google adds "an extra step to confirm your identity" when a device it has not seen before signs in ([Investigate suspicious activity][suspicious-activity]), so the account's password and second factor are needed at that moment. Each machine's AVD is a new device to Google; copying a signed-in AVD between machines was not tried and is _unverified_.

How long such a sign-in stays valid. Google documents no lifetime for a device's account sign-in. Documented ways it ends:

- A password change or reset signs the account out "everywhere except" verifying devices and some third-party apps ([Change your password][change-password]).
- Google may ask to verify the account for sensitive actions and may block the action for 7 days if that fails ([Verify it's you][verify-sensitive]).
- An account unused for two years is deleted; signing in with Sign in with Google counts as activity ([Inactive account policy][inactive-policy]), so a regularly run suite keeps it alive.
- Google may "suspend or terminate your access" or delete an account that breaks its terms ([Google Terms of Service][google-tos]).

Every read-only run resumes the snapshot's device state and refreshes tokens that are then thrown away; whether Google eventually invalidates the snapshot's device credentials because they are replayed from the same starting point, possibly on several machines at once, is _unverified_. The emulator's clock was current right after loading the snapshot in the probe (it showed the host's time), so clock drift did not appear; a long-lived snapshot's behavior over weeks is _unverified_.

Anti-automation measures. Google publishes no rules for test accounts on emulators. Its help pages describe sign-in challenges for new devices and "unusual" sign-ins and security alerts on the account's other devices ([Investigate suspicious activity][suspicious-activity], [Protect your account][unfamiliar-activity]); community reports link such alerts to emulators, without confirmation from Google. Google's terms forbid "creating fake accounts" and "using automated means to access content from any of our services in violation of the machine-readable instructions" ([Google Terms of Service][google-tos]). A real, dedicated account that a person created and signs in by hand, then used through the official app flow, does not obviously fall under either; automating the account's own sign-in (typing the password into Google's page from a script) is where CAPTCHA, phone verification and account blocks would apply, and the suite should not do it. These are judgments from Google's general pages, not a statement by Google.

## Can UI Automator or Appium drive Google's flow?

Every screen of the flow runs in `com.google.android.gms` (`CredentialChooserActivity`, `GoogleSignInActivity`, `MinuteMaidActivity` in the probe), not in Cup. UI Automator is Google's framework "for cross-app functional UI testing across system and installed apps" ([UI tests][ui-tests]), and the Appium UiAutomator2 driver forwards native commands to it ([sibling research on E2E tools](https://github.com/patricktree/cup/issues/180)). In the probe, `uiautomator dump` exposed the add-account screen: `com.google.android.gms` nodes with resource IDs such as `com.google.android.gms:id/minute_maid` and `suc_footer_button_bar`, buttons with text `NEXT` and `SKIP`, and a WebView titled `Sign in - Google Accounts`. `screencap` captured it, so that screen did not set `FLAG_SECURE`. Pressing Back with `adb shell input keyevent 4` cancelled it as described above.

The account chooser and consent screens shown with an account on the device were not reached, so whether they expose an account row and "Continue" button to UI Automator, or set `FLAG_SECURE`, is _unverified_. Their labels belong to Google and change with Play services updates, so selectors should key on the account's email text rather than resource IDs; Google's UI after a fresh grant (consent) differs from a returning one (no consent), which the read-only snapshot fixes at the state it was saved in.

## Turning the real ID token into a Cup session

In the app the token goes from the plugin to Supabase's `signInWithIdToken`; Supabase verifies it and returns a Supabase session, which the Worker accepts when `app_metadata.provider` is `google` ([authentication architecture](../architecture/authentication.md)). Google's verification rules: the signature checks against Google's keys at `https://www.googleapis.com/oauth2/v3/certs`, `aud` equals one of the app's client IDs, `iss` is `accounts.google.com` or `https://accounts.google.com`, and `exp` has not passed ([Verify the Google ID token][verify-id-token]). The `nonce` claim echoes "the value of the `nonce` supplied by your app" ([OpenID Connect][oidc]), which here is the SHA-256 hex digest Cup passes; Supabase compares it with the hash of the raw nonce Cup sends, unless `skip_nonce_check` is set ([Supabase: Login with Google][supabase-google]). The local stack already sets `skip_nonce_check = false` and reads the Google client ID from `SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_ID` ([`supabase/config.toml`](../../supabase/config.toml)), where the test project's web client ID would go first in the comma-separated list ([Supabase][supabase-google]).

A local fake auth provider standing in for Supabase would do the same checks: fetch Google's JWKS (the API server already uses `jose`'s `createRemoteJWKSet` for Supabase tokens), require the test web client ID as audience and Google's issuer, compare the nonce hash, then mint the Supabase-shaped session the Worker expects. Either way the run needs internet for Google's sign-in and keys. Google ID tokens are "valid for up to 1 hour" ([Google Cloud token types][token-types]), which is ample because Cup exchanges the token immediately; the nonce is fresh per sign-in, so a token cannot be replayed into a later test.

## Google's guidance on testing

Google publishes no testing guide for Sign in with Google or Credential Manager. The androidx Credentials library ships no testing or fake artifact: its release notes list only `credentials`, `credentials-play-services-auth` and the deprecated `credentials-e2ee`, and the "test API" entries of `1.2.0-beta01` are provider-side helpers ([androidx Credentials release notes][credentials-releases]). No `TestCredentialManager` exists there. The troubleshooting guide notes that its exceptions "apply to emulators as well" ([troubleshooting][troubleshooting]). Google's general testing advice favors many small tests with fakes and few large tests, and its Automated Test Device images drop Google apps on the assumption that "other apps or the platform will function correctly" ([sibling research on E2E tools](https://github.com/patricktree/cup/issues/180)), which points toward faking Google in Cup's suite rather than driving it. Credential Manager's Kotlin `CredentialManager` is an interface that native code could fake, but Cup calls it only inside the plugin, so a fake would have to replace the plugin.

## Recommendation

Do not complete a real Google sign-in in the automated suite. Open Google's flow, check that it appears, dismiss it, and fake the rest.

1. **Per-machine Google Cloud setup is real today, and avoidable.** Each machine's generated debug keystore needs its own Android OAuth client. A committed debug keystore with `signingConfigs.debug`, registered once in a **separate test project** whose web client ID production Supabase does not accept, removes that step without exposing production. If real sign-in is ever wanted (for example as an opt-in manual check), set it up this way, never on production's project.
2. **Real sign-in would still cost per machine.** One-time: a test Google Cloud project, a web and an Android client, a dedicated Google account, the committed keystore, and Supabase configured with the test web client ID. Per machine: a person signs the account into a suite-owned AVD with its password and second factor, completes one consent and saves the snapshot, again after any password change, Google challenge or lost snapshot. Ongoing: the account's password as a secret outside the repository, Google's unannounced UI changes in Play services, possible challenges or blocks for a device replayed from a snapshot on several machines, the OAuth client's 6-month inactivity deletion, internet on every run, and tests that cannot be retried under the repository's rule when Google interrupts. The map rules out real accounts for the suite, and this confirms why.
3. **Opening the flow works without any of this.** With no account on the device and an unregistered SHA-1, Cup's "Continue with Google" opened Google's add-account screen in Play services, UI Automator read it, and Back returned `SIGN_IN_CANCELED`. A test can assert that Google's flow opened (the focused window's package is `com.google.android.gms`, or the `minute_maid` resource ID is present), press Back, and assert that Cup handled the cancellation, then continue with a fake sign-in for the session tests. It needs internet for Google's page, and it must tolerate Cup's WebView reloading after cancellation, which happened once in the probe; whether Cup's state survives that is worth a check in [How the apps sign in during automated tests](https://github.com/patricktree/cup/issues/183).

Open points: what the account chooser and consent screens expose to UI Automator, the exact error for an unregistered SHA-1 with Credential Manager `1.5.0`, how long a snapshot with a signed-in account keeps working, and why Cup's WebView restarted after the cancellation.
