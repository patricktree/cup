# Gate cache trust and mobile E2E parallelism

> Historical investigation, incorporated 2026-11-10. It is the evidence behind [ADR 0020](../adr/0020-validate-in-three-local-gates-that-trust-the-turbo-cache.md), which lets every validation gate accept Turbo cache hits and runs mobile E2E in the deploy gate. The project differed from it in two places: all three cache gaps were fixed, gap 4 included, in [`917158c6`](https://github.com/patricktree/cup/commit/917158c6), and the Appium driver installation took a cross-process lock rather than a home per driver. The parallel runner and the `cap sync` check were built in [#255](https://github.com/patricktree/cup/pull/255); the [mobile E2E README](../../qa/mobile-e2e/README.md#parallel-platforms) has the current state. [Original](https://github.com/patricktree/cup/blob/72273c3d3b1742e5036b87b8366f11b32a92ad35/docs/research/gate-cache-and-mobile-parallelism.md) on the unmerged branch `research/gate-cache-and-mobile-parallelism`.

Research date: 2026-11-10, for [issue #233](https://github.com/patricktree/cup/issues/233) of the [validation gates map](https://github.com/patricktree/cup/issues/232). Repository observations are from `0a126330`, checked again against `origin/main` at `549f7927`, which differs only by the `@cup/workspace-checks` fix `258d4f45` and two unrelated commits. Tool versions: Turbo 2.11.7, Vitest 4.1.11, `@cloudflare/vite-plugin` 1.62.2. Machine: Apple Silicon Mac with 14 cores (10 performance) and 36 GB of RAM.

Evidence comes from the configuration and source files cited below, from `pnpm exec turbo run turbo:build turbo:lint turbo:test turbo:cf-typegen --dry=json`, and from probes that appended a comment line to one file, ran the dry run again, compared the task hashes and restored the file. No emulator, simulator, E2E suite or test task was run: another session was using the devices on this machine.

## Question

1. **Cache trust.** Which `turbo:build`, `turbo:lint`, `turbo:test` and `turbo:cf-typegen` tasks read files outside their cache inputs, so that Turbo could replay a stale passing result, as `@cup/workspace-checks` did?
2. **Mobile parallelism.** Can the Android and iOS projects of `qa/mobile-e2e` run at the same time on one Mac, and what wall-clock time does that give compared with 3 min 31 s plus 4 min 50 s in sequence?

## Answer

1. Besides the known `@cup/workspace-checks` case, now fixed on `main`, three gaps remain. Two let a test replay a stale pass: the Durable Object storage libraries' tests read a docs page, and the Worker's tests read a Terraform file, and neither file is an input of those tasks. The third replays a stale file into a build output, `.dev.vars` in the Worker's `dist`, but no gate reads it. Everything else that tasks read outside their package is a declared workspace dependency, a global dependency, or not read by any task.
2. Yes, as two Vitest processes, one per project, after one shared workspace build. A single Vitest run cannot run them at the same time as configured: Vitest sets up the two projects one after the other and then runs every spec in one sequential group. The suite already isolates devices, ports and test Workers for concurrent runs from several checkouts. Within one checkout the only shared state that races is the Appium driver installation on a first run. Expected wall-clock time: about 5 to 5.5 minutes instead of 8 min 21 s, bounded below by iOS's 4 min 50 s.

## How Turbo hashes these tasks

The root [`turbo.jsonc`](https://github.com/patricktree/cup/blob/0a126330/turbo.jsonc) gives `turbo:build`, `turbo:lint` and `turbo:test` the inputs `$TURBO_DEFAULT$` minus `*.md` and `LICENSE`, and `apps/cloudflare-worker/wrangler.jsonc` as a global dependency. The shared stack's [`config-turbo-typescript/turbo.jsonc`](https://github.com/patricktree/patricktree-stack/blob/fb6ee7c06dbd62ccd101ee1bcd49ccb7f38ac238/tooling/config-turbo-typescript/turbo.jsonc), which every package extends, turns caching on, makes each task depend on `^turbo:build`, and adds `$TURBO_ROOT$/.patricktree-stack/tooling/config-oxlint/**` and `$TURBO_ROOT$/tooling/config-oxlint/**` to the lint inputs. Eight packages add `turbo:cf-typegen` to their task dependencies. The dry run's global inputs are `.gitattributes` and that `wrangler.jsonc`.

`$TURBO_DEFAULT$` is the package's Git-tracked files and untracked files Git does not ignore, so a task's inputs never include a file outside its package, a `.md` file, or a Git-ignored file such as `.env.local`, `dist/` or `worker-configuration.d.ts`. A dependency task's hash is part of the dependent task's hash, so reading a declared dependency's built output or sources is covered.

The dry run reports `envMode: strict` for every task and no `env`, `passThroughEnv` or `globalEnv` anywhere. In strict mode a task gets only Turbo's built-in system variables, so an environment variable cannot make a replay stale: an undeclared variable is absent from every run, cached or not. The variables tasks read are `CI` in `apps/web-app/playwright.config.ts`, which strict mode leaves unset, and `CUP_UI_GALLERY_PORT`, `INIT_CWD` and `npm_lifecycle_event`, which Playwright and pnpm set inside the task.

Fixes, for the spec to choose from:

- Gaps 2 and 3: add the file to the task's inputs in the package's `turbo.jsonc`, for example `"turbo:test": { "inputs": ["$TURBO_EXTENDS$", "$TURBO_ROOT$/docs/architecture/durable-object-storage.md"] }`. That costs nothing. Alternatively, turn caching off as for `@cup/workspace-checks`, but the Worker tests are not fast.
- Gap 4: exclude the file from the outputs (`"!dist/**/.dev.vars"`), so it is never cached or restored. Or accept the gap, since no gate reads the file.

## Checked and not gaps

- **Shared configuration packages** (`config-typescript`, `config-vitest`, `config-playwright`, `config-oxlint`, `config-stylelint`, `config-wyw-in-js`) have no task scripts, but a change to them still invalidates every task. The probe on `config-vitest/vitest-base.js` moved every tracked hash, through the global `hashOfInternalDependencies`, because the root package depends on them through `@cup/config-oxlint` and the stack's tools. A probe on `tooling/config-oxlint/oxlint-base.js` did the same. Every `@cup/*` or `@patricktree-stack/*` package named in a package's `tsconfig*.json`, `*.config.*` or `vite.*.ts` is also a declared dependency of that package (a script over every workspace package found none missing).
- **`apps/cloudflare-worker/wrangler.jsonc`**, which `@cup/audiobook-production#turbo:cf-typegen` reads, is a global dependency. The probe moved every hash.
- **Generated Worker types read across packages**: the `tsconfig` files of `@cup/api-server` and `@cup/create-audiobook-from-url-workflow` load `../conversion-grants/worker-configuration.d.ts`. Both declare `@cup/conversion-grants`, whose `turbo:build` depends on its `turbo:cf-typegen`, so the chain carries the hash.
- **`qa/test-worker/wrangler.jsonc`** serves `../../apps/cloudflare-worker/dist/client`, the built output of a declared dependency, and its `turbo:test` does not start Wrangler.
- **Root files**: the root `oxlint.config.ts` is not an input, but package lint does not load it. `oxlint --print-config` in `libs/errors` shows none of its `options`. No task reads `pnpm-workspace.yaml`, `knip.ts` or `.markdownlint-cli2.mjs`. A catalog version change reaches the lockfile and so the external-dependency hash.
- **Other repository-root reads**: `@cup/env-setup`'s tests run against a temporary directory. `@cup/operator`'s CLI test resolves the repository root only to find its own `src/cli.ts`. `@cup/brand-assets` and `env-setup`'s `dev-services.ts` read the root only from scripts no Turbo task runs. The unit tests of `qa/mobile-e2e` and the Vitest tests of `qa/e2e` read no files.
- **Excluded `*.md` in a package's own folder**: no task reads its own package's Markdown files.

A static review cannot rule out a read it did not search for. A gate that must not trust the cache could also run `turbo run ... --force` before a deploy as a backstop. For the pre-review gate that costs the uncached 7 minutes.

## Mobile E2E parallelism

### Why one Vitest run is sequential

[`qa/mobile-e2e/vitest.config.ts`](https://github.com/patricktree/cup/blob/0a126330/qa/mobile-e2e/vitest.config.ts) defines the `android` and `ios` projects, each with its own global setup, and sets `fileParallelism: false`. In Vitest 4.1.11 (`vitest/dist/chunks/cli-api.CnMVyzaz.js` and `coverage.DM_a_rWm.js` in the installed package):

- `initializeGlobalSetup` awaits each project's global setup in turn (`for (const project of projects) await project._initializeGlobalSetup()`). Android's setup builds the APK, boots the emulator and starts Appium. Only then does iOS's setup build the app, create the simulator and start Appium.
- `fileParallelism: false` sets `maxWorkers` to 1, and `groupSpecs` puts every isolated spec with `maxWorkers === 1` into one shared group with one worker. The specs of both projects therefore run one after another, while both devices stay up.

`sequence.groupOrder` only orders such groups, and one group with two workers would run two specs of the same project on one device. One Vitest process cannot give one worker per project and two at a time. Running each project in its own process can.

### Estimate

In sequence the two platforms take 3 min 31 s plus 4 min 50 s, 8 min 21 s (map #232, measured on 2026-11-10 one platform at a time). Each measurement includes the cached workspace build, a few seconds that a parallel run pays once. In parallel, iOS is the critical path, so 4 min 50 s is the lower bound. Both app builds, Gradle and `xcodebuild`, then overlap with the emulator boot, a 4 GB guest, and with the simulator for about the first minute. After that both test phases run at once, until Android finishes at about 3.5 to 4 minutes. The README already observed iOS runs of 4 min 40 s to 4 min 46 s while other checkouts loaded the Mac, so contention costs something. With 10 performance cores and 36 GB, an iOS slowdown of 5 to 15 percent while Android runs is a reasonable guess, not a measurement. That gives **about 5 to 5.5 minutes, saving about 3 minutes (35 to 40 percent)**.

The risk is load: tests are never retried, so a timeout caused by the load fails the gate. Several consecutive warm parallel runs that all pass should come before the gate relies on it.

### What would need to change

1. **Runner**: build the workspace once, then start `vitest run --project android` and `vitest run --project ios` as two processes. Prefix or separate their output, wait for both and fail when either fails. A small Node script in `qa/mobile-e2e` behind the root `test:e2e:mobile` would do this. `--project <name>` keeps running one platform.
2. **Appium drivers**: make the installation safe to run concurrently. Take a lock around `ensureDriver` as `emulator.ts` does for its snapshot, or give each driver its own `APPIUM_HOME` (`.appium/uiautomator2`, `.appium/xcuitest`), or install both drivers before the two processes start.
3. **Check `cap sync`**: confirm with one parallel run that `cap sync android` and `cap sync ios` write no file in common.
4. **Docs**: update the README's run, runtime and isolation sections, and note the parallel run where ADR 0018 or the validation docs describe how the suite runs.
5. **Verification**: several consecutive warm parallel runs that all pass, timed against the 8 min 21 s.

## Limits

- The cache review is static plus hash probes. It searched for paths that leave a package (`../..`, repository-root helpers, `import.meta.dirname`, `process.cwd()`), environment-file reads and generated files. It cannot prove that no other read exists.
- The probes appended comments. Turbo hashes file contents, so a comment counts as a change, but the probes did not check what each test would then report.
- The parallel estimate is derived from sequential measurements. Nothing was run in parallel.
