# Test Worker

This package holds the test-only Worker that the E2E suites run against, the helper that starts it, and the fake auth provider. The [application E2E tests](../e2e/README.md) and the [mobile E2E tests](../mobile-e2e/README.md) use it; a change to a fake or to the harness lands here once for every suite.

- The [Worker entry](worker/worker.ts) runs the production API server, Durable Objects and Workflows, and replaces source-material preparation, narration selection, and speech synthesis with deterministic fakes. Each fake belongs to the production library whose boundary it implements. The `QA_SCENARIO` variable selects how the fakes behave, such as a failing speech provider. In `tts-failure` the speech fake answers with a 400 that the production synthesis code treats as permanent, so the segment Workflow fails at once instead of waiting out its production retry backoff (5 and 10 seconds); the Workflow keeps no test-only path, and [its library tests](../../libs/create-audiobook-from-url-workflow/test/provider-failure.test.ts) cover a retried 503 with the production retry count. The speech fake synthesizes one continuous tone that its speech recognition hears no words in, so under speech policy 7 every segment after the first finds no cut point and falls back to its narration chunk alone, a second synthesis request; `/__qa/speech-calls` reports each request with its segment sequence, and the E2E tests count synthesized segments rather than requests. The Worker's [Wrangler configuration](wrangler.jsonc) serves the built web app from the Worker's assets.
- [`startTestWorker`](src/test-worker.ts) starts one `wrangler dev` process on a port the operating system assigns, with its own persistence directory. A suite starts one per test, so tests can run in parallel and in several checkouts at once. With `https` it serves HTTPS with a given key and certificate, as the [web suite](../e2e/README.md#browsers-and-https) needs for WebKit; the mobile suite uses HTTP. The Worker entry logs each request it receives, with the body of a POST, and the helper reads that log back, so a suite can check what its client sent. The helper can restart the Worker with another scenario, create a conversion grant through the operator API, and keep the persistence directory after a failed test.
- [`startAuthProvider`](src/auth-provider.ts) is a local stand-in for Supabase Auth: real PKCE, signed access tokens and JWKS, with no Google traffic. Pass its origin to `startTestWorker` so the Worker verifies its tokens; its origin is also its token issuer. By default it listens at `http://127.0.0.1:<port>`. With `hostname: "localhost"` it listens on both the IPv4 and the IPv6 loopback and issues tokens for `http://localhost:<port>`, as the mobile suite needs. With `tls` it serves HTTPS instead; the web suite passes the certificate its Worker serves, because WebKit blocks an HTTPS page from calling HTTP.
  - For native Google sign-in, it stands in for Google too: `POST /qa/google-id-token` returns a Google ID token carrying the nonce it was sent, and the `grant_type=id_token` exchange accepts that token only with the raw nonce whose SHA-256 hash it carries, then returns the same Google-provider session as the PKCE exchange. The Android debug build's sign-in fake calls the first; the web app's `signInWithIdToken` calls the second.
  - It refreshes sessions as Supabase does: every session carries a new single-use refresh token, and the `grant_type=refresh_token` exchange trades it for a new session of the same sign-in, with a new access token and a new refresh token. As in Supabase, a second use within the reuse interval, 10 seconds by default, returns the session the first use issued, so a page that reloads during a refresh and still holds the old token stays signed in. A later second use is rejected with `refresh_token_already_used`, and a token it never issued with `refresh_token_not_found`, both as HTTP 400 in Supabase's error shape: `{ code, message }` with an `X-Supabase-Api-Version: 2024-01-01` header when the client sends that version, as supabase-js does, and the legacy `{ code, error_code, msg }` otherwise. `setRefreshTokenReuseInterval(seconds)` changes the reuse interval, so a test can see a later reuse rejected without waiting 10 seconds. `refreshes()` counts the refreshes that issued a new session, not the reuses; `exchanges()` counts only sign-ins.
  - It signs in the local test account ([ADR 0012](../../docs/adr/0012-offer-a-local-test-account-instead-of-google-in-development.md)) as Supabase's email provider: the `grant_type=password` exchange accepts only the credentials in `TEST_ACCOUNT` and returns an email-provider session with the `amr` method `password`, which refreshes like any other; other credentials get `invalid_credentials`. `startTestWorker({ offersTestAccount: true })` sets the Worker's `LOCAL_TEST_ACCOUNT_*` to those credentials, so its auth configuration offers "Sign in with test account" and it accepts the account's tokens; without it they stay empty. The web suite's `offersTestAccount` fixture option passes it on.
  - `authorizationRequests()` returns the query parameters of every request to `/auth/v1/authorize` so far, in order and including rejected ones, such as the `prompt` and `max_age` the app passed to Google.
  - Access tokens stay valid for 300 seconds. `setAccessTokenLifetime(seconds)` changes the lifetime of the access tokens issued from then on, also on refresh, so a test can see a session refresh within its time budget.
  - Both suites hand each test its provider: the web suite as `workerEnvironment.authProvider` from its [fixtures](../e2e/test-e2e/fixtures.ts), the mobile suite as `authProvider` from [`useMobileApp`](../mobile-e2e/src/fixtures.ts). A test configures it before the app signs in.

The Worker serves `apps/cloudflare-worker/dist/client`, so build the workspace before a suite starts it.

The package's own [Vitest tests](test/) check the fake auth provider, such as its reachability over both loopbacks, the nonce check of the ID token exchange, the refresh grant, its reuse interval and its rejection of tokens reused after it, the recorded authorization parameters, the access token lifetime and the test account's password grant; `pnpm test` and every [validation gate](../../AGENTS.md#validation-gates) run them.

## Cost and network boundary

This boundary applies to every suite that uses this package. The test Worker has no Cloudflare AI binding and refuses to run a workflow when an AI binding or Cloudflare credential reaches it. The helper removes Cloudflare account credentials from each Wrangler child process. Do not add a paid-provider binding or a real provider call to this package. A local deterministic fake is the required test seam, even when it gives less confidence than a paid integration test.

Each suite also keeps its client from reaching other hosts; the web suite rejects unexpected browser requests.
